# Synthesized Context

## PRD 实施检视与已知缺口

- 主题：注册验证码系统消息、最终文本内容审核、投诉统计数据质量、试用额度与计费衔接、容量与投诉归属边界。
- 用途：作为下游路线规划的现状与风险上下文；不覆盖 PRD 的目标需求。
- source: docs/PRD_REVIEW.md

### 原文记录

```markdown
# PRD 检视记录（superpowers 式复盘）

针对 `PRD.md`（ycsansms.md v1.3.0）在启动本次工程实现前所做的系统性检视，
按"找根因、不只挑表面问题"的方式整理，供后续迭代时对照修复。

## 🔴 主要问题

1. **注册验证码存在循环依赖**——机构注册时联系人手机号需要短信验证码核验真实性
   （F-2.1），但发送验证码短信要求已审核通过的签名+模板（F-3.7 硬性要求），而一个
   尚未完成认证的新机构不可能已有审核通过的签名模板。PRD 未定义"平台系统消息通道"
   （用于注册验证码、审核结果通知等平台侧自发消息）。
   **本次实现的应对**：`Template.isSystemTemplate` 字段 + `MessageSubmitService` 里
   放行系统模板跳过机构归属校验，但*审核免除*的完整策略仍待补（当前系统模板需要
   预先在数据库手工插入并标记 `APPROVED`）。

2. **内容审核的覆盖边界未定义**——敏感词库到底是只在模板审核时查一次，还是每次发送
   都要对"拼接后的最终文本"（含用户填入的变量）实时扫描？如果不扫变量，用户可以在
   验证码模板的变量位置注入广告文字绕过审核。
   **本次实现的应对**：`MessageSubmitService.renderContent()` 先把签名+模板+变量渲染
   成最终文本，再传给 `ContentReviewChecker`——即"扫描最终文本"这一决策已经代码化，
   写在 `RoutingContext` 的 Javadoc 里，避免未来有人"优化"成只扫模板原文。

3. **投诉占比的数据质量依赖人工登记**——F-11.9 的分子完全来自 F-9.1 人工登记的工单，
   一旦运营录入不及时，占比会失真滞后。
   **本次实现的应对**：无代码层面的应对（这是产品/运营流程问题）；在
   `ComplaintRatioService` 类注释里明确记录了这个限制，避免有人误以为这个数字是实时/
   自动化采集的。

4. **试用额度与计费模块未打通**——F-2.8 试用条数额度与 F-8 预付费扣费是两套独立机制，
   试用期内的发送是走独立的额度计数，还是也要生成 `billing_record`（金额为 0）？
   **本次实现的应对**：`TenantService.tryConsumeTrialQuota()` 独立于 `BillingService`
   实现，`MessageSubmitService` 当前**没有调用**这个方法（即试用期机构目前会被当成
   已签约机构一样走预付费扣费，行为不完全对——这是一个需要后续修的真实 bug，
   已记录在 core/docs/ROADMAP.md）。

## 🟡 次要问题

5. 验收标准（PRD 第 11 章）把"10 万条基线"这个已知待确认的数字直接写进了验收门槛，
   建议加一句"具体数值以评审确认结果为准"。
6. 投诉工单若未关联具体通道/机构（如纯内容类投诉）时，如何计入 F-11.9 占比分子，
   未定义边界情况——`Complaint.channelId`/`tenantId` 均可为 null，
   `ComplaintRepository.countByChannelIdAndCreatedAtBetween` 传 null 时的行为未测试。

## 假设记录（PRD 里已标注，此处汇总便于查找）

- "千分之三"投诉占比阈值：PRD 表述"千万三"有歧义，按行业常见的千分之三（0.3%）理解，
  已设为可配置默认值（`application.yml` 的
  `ycsopen.routing.complaint-ratio-threshold: 0.003`）。
- "单日 10 万条"与"1000 条/秒"两个容量指标数量级不一致，PRD 已按"最低容量基线、
  非上限"处理，本次实现未对此做任何硬编码限制（没有代码去人为限制日发送量为 10 万条）。
```
