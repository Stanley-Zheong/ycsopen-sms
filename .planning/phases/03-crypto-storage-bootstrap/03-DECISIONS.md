## DR-P03-001 — YCSE/v1 capacity and in-place representation

- **Decision:** `ENVELOPE-CONTRACT.md` is the single canonical YCSE/v1 binary, authenticated-header, domain-separated AAD, capacity and allocation contract. It fixes provider ID `pkcs11` (6 bytes), a canonical key reference of at most 32 ASCII bytes, the exact 19-byte header, authenticated declared lengths, 12-byte wrap/data nonces, 48-byte wrapped DEK, 16-byte data tag and 145-byte maximum overhead. A V1 `VARBINARY(255)` cell accepts at most 110 plaintext bytes. Registration objects have purpose-specific 5 MiB or 10 MiB plaintext limits and maximum complete envelope lengths of 5,243,025 or 10,485,905 bytes. A MySQL dump uses canonical `mysql-encrypted-snapshot-chunk` envelopes rather than one in-memory object: each chunk is at most 10,485,760 plaintext/10,485,905 envelope bytes, while one snapshot is bounded to 1 TiB plaintext, 104,858 chunks, and 1,099,526,832,186 total envelope bytes.
- **Evidence:** `03-RESEARCH.md` “Open Questions (RESOLVED)” capacity table; V1 declares every reversible protected DB cell as `VARBINARY(255)`; PRD declares phone as 11 digits and identity number as 18 characters.
- **Alternatives rejected:** shrinking authenticated metadata, truncating values, context-free side tables, editing V1, or silently assigning a current target to a future owner.
- **Consequences:** phone and identity targets fit. Credential writers enforce a 110-byte UTF-8 ceiling. Database/object/snapshot readers reject declared/actual over-limit input, u32/u64 checked-add overflow, oversized provider/key-reference/context fields and trailing bytes before length-derived allocation. Data AAD binds a stable header with the rotatable key-reference length normalized to zero; wrap AAD binds the complete header and actual key reference. This permits metadata-only DEK rewrap without unsafe data-key/nonce reuse while the two AEAD tags still authenticate the complete envelope. Snapshot creation and restore stream one independently authenticated chunk at a time, bind migration/snapshot/chunk identity in AAD, and reject missing, duplicate, reordered, truncated, extra or post-final chunks; whole-dump `readAllBytes()` and plaintext dump files are forbidden. Every authenticated-header field has a tamper mutation under its applicable AEAD domain. Any existing larger value, noncanonical key reference, or real-MySQL binding mismatch is a blocking TODO and prevents OBL-001/004 evidence.
- **Scope:** all V1 reversible protected DB targets; no cross-owner DDL.

## DR-P03-002 — Production adapter and SoftHSM evidence boundary

- **Decision:** the production key port is Java 21 SunPKCS11 over PKCS#11. SoftHSM 2.7.0 is protocol-conformance evidence, not physical-HSM certification. YCSE/v1 KEK wrapping uses random 96-bit AES-GCM nonces and a conservative hard ceiling of 1,048,576 reserved wrap operations per KEK reference. At count 983,040 the Phase-owned key row atomically enters `ROTATION_REQUIRED`; at 1,048,576 every new wrap is rejected until another key is ACTIVE.
- **Evidence:** official immutable GitHub release tag `2.7.0`, commit `13e6e86`; admitted codeload archive SHA-256 `be14a5820ec457eac5154462ffae51ba5d8a643f6760514d4b4b83a77be91573`; Oracle Java 21 SunPKCS11 documentation cited in research.
- **Alternatives rejected:** application-held KEK bytes, deterministic production fallback, an unselected vendor KMS SDK, moving package-manager/source fallback, or claiming SoftHSM as certified hardware.
- **Consequences:** provisioning must verify the exact archive before extraction/build, install into a run-owned destination, identify the exact library and CLI, initialize a run-owned token, test mechanisms/key attributes, and clean every run-owned resource. `KeyProtectionPort.wrap` is the only caller-visible wrap operation. Its production adapter is the sole owner of the ordered sequence: durably reserve one monotonically increasing V1200 operation, generate the wrap nonce, invoke the provider, and return one immutable key-reference/nonce/wrapped-DEK result. The codec cannot invoke admission, provide a wrap nonce or retry a failed wrap; failed operations consume their reservation, counts never decrement or reuse, and concurrent/restarted callers cannot cross the ceiling. A persisted activation is not a completed runtime cutover until the adapter is reconstructed or the process restarts with the new ACTIVE and old DECRYPT_ONLY/RETIRING descriptors; a stale adapter must fail before issuing, wrapping or committing under its obsolete ACTIVE view. Deployment supplies its vendor module/token/HA/IAM binding through the same fail-closed port.
- **Scope:** key protection and blind-index operations only.

## DR-P03-007 — Blind indexes use Phase-owned multi-version metadata

- **Decision:** all new keyed mobile indexes are canonical 33-byte version-plus-HMAC values encoded as 53 lowercase Base32 characters and stored in Phase-owned `ycs_crypto_blind_indexes`; no legacy `CHAR(64)` cell stores two versions or a new raw mobile SHA-256. The table binds `target_type`, `legacy_row_id`, `field_id`, `key_version`, `index_value`, and `status` with one row per logical target/key version. Its unique key is `(target_type, legacy_row_id, field_id, key_version)` and its lookup key is `(target_type, field_id, status, key_version, index_value)`. The polymorphic legacy binding cannot have a cross-table SQL foreign key, so the reviewed target manifest, same-transaction existence check, original-row digest, and orphan reconciliation are the mandatory binding proof; `key_version` is foreign-keyed to the Phase-owned key-reference registry.
- **Compatibility:** HMAC input schema `mobile-sha256-v1` first normalizes an 11-digit mobile, computes the historical 32-byte SHA-256 in memory, and HMACs that value with target/field/purpose context. This lets migration recompute indexes even for an audit row that retained only the historical digest. Readers compute every ACTIVE and RETIRING key version, query the metadata table with an `IN`/union, and may union a raw-SHA legacy query only while that exact target checkpoint is not `COMPLETE`. A completed target rejects legacy fallback.
- **Migration:** the exact current legacy-index targets are `mobile_portability.mobile_hash`, `blacklist_entries.mobile_hash`, `third_party_risk_check_logs.mobile_hash`, `message_tasks.mobile_hash`, and `unsubscribe_records.mobile_hash`; protected mobile columns without a `mobile_hash` are field-encryption targets but not invented equality indexes. `third_party_risk_check_logs.mobile_hash` is a V1 `CHAR(64)` indexed `MIGRATABLE_SCHEMA_ONLY` surface: current Java has no reader/writer, but deployed databases may contain historical rows, so it remains in migration/scrub evidence and its writer fence must prove no unknown external writer. Each target advances `DISCOVERED -> BACKFILLED -> VERIFIED -> CUTOVER -> SCRUBBED -> COMPLETE`. Backfill inserts metadata idempotently; cutover requires a compatible deployed-writer fence; scrub replaces legacy `CHAR(64)` raw digests with non-queryable row-binding locators and atomically updates any locator-based metadata binding. Blacklist and portability targets must prove query hits before backfill, during dual-read compatibility, and after HMAC-only cutover on real MySQL. Concurrent legacy writes, checkpoint drift, duplicate key-version rows, or missing bindings block advancement and leave the earlier reader mode intact.
- **No-index protected targets:** `bulk_sending_items.mobile_encrypted` and `uplink_records.mobile_encrypted` remain mandatory protected-field inventory and in-place migration targets. V1 gives neither table a `mobile_hash` companion and current source exposes no equality-query contract for either field, so they are explicitly excluded from blind-index metadata. This exclusion does not permit their omission from encryption, migration, raw-row scan or OBL-001/004 evidence; the inventory/evidence producer rejects either target disappearing from the protected union.
- **Legacy implementation:** the global `HashUtil` API is not a production query owner. Before every current target is complete, the only raw-SHA computation is an explicitly named `LegacyMobileHashReader` guarded by the target checkpoint; after completion it is unreachable and removable. New writes persist a non-queryable 64-character row locator in required legacy columns and persist each current write-compatible ACTIVE/RETIRING HMAC version as a separate metadata row. Mixed-version writer compatibility ends only when the signed writer fence and per-version backfill prove older readers are absent; no logical value is concatenated into one cell.
- **Evidence:** migration and rotation tests prove one metadata row per active/retiring version, no single-cell dual write, fallback disabled after completion, rollback to the last verified checkpoint before cutover, and forward recovery from an encrypted snapshot after scrub.
- **Scope:** Phase-owned metadata and compatibility logic only; V1 DDL remains immutable.

## DR-P03-008 — Migration preflight consumes signed, replay-resistant manifests

- **Decision:** production `WriterFencePort` and `EncryptedSnapshotVerifier` implementations accept exactly one inseparable writer/snapshot pair from bounded canonical JSON manifests and detached Ed25519 signatures at explicit canonical CLI paths. Both manifests carry the same canonical `migration_set_id`, environment, database-instance fingerprint, schema, Flyway-set digest, unsigned 64-bit global sequence and `signer_key_version`. Deployment config provides a pinned fingerprint set of exactly one `ACTIVE` Ed25519 X.509 trust anchor plus zero or more `RETIRING` anchors; `RETIRED`, `REVOKED`, unknown, duplicate-version, duplicate-fingerprint and unpinned keys fail closed. Symlinks, non-regular files, duplicate/unknown JSON fields, noncanonical encoding, unbounded files, fingerprint drift and invalid signatures fail closed.
- **Canonical pair:** compute `writer_digest` and `snapshot_digest` as SHA-256 of each manifest's canonical bytes. Compute `pair_digest = SHA-256(ASCII("YCS-MIGRATION-PAIR/v1\u0000") || length-prefixed migration_set_id || length-prefixed canonical environment/database/schema/Flyway subject || u64 sequence || length-prefixed signer_key_version || writer_digest || snapshot_digest)`. The writer detached signature covers `ASCII("YCS-MIGRATION-PAIR-SIGNATURE/v1\u0000") || 0x01 || pair_digest || writer_digest`; the snapshot signature covers the same prefix with role byte `0x02`, the same pair digest and `snapshot_digest`. Both signatures must verify with the same signer version. This commits each independently schema-valid manifest to the exact other manifest without a circular JSON field.
- **Writer manifest:** schema `ycs-writer-fence/v1` binds the shared pair fields, issued/expiry markers, and a nonempty unique writer set of artifact ID, version, source digest and migration-compatibility declaration. Empty, unknown, stale, future, duplicate or incompatible writers are rejected.
- **Snapshot manifest:** schema `ycs-encrypted-snapshot/v1` binds the shared pair fields, canonical `snapshot_id`, admitted recovery key reference, completed marker, checked total plaintext/ciphertext sizes, ordered chunk count, and one bounded record for every `mysql-encrypted-snapshot-chunk`: zero-based index, final flag, plaintext size, complete-envelope size and SHA-256 digest. The limits and AAD identity come only from `ENVELOPE-CONTRACT.md`. Missing, duplicate, reordered, truncated, extra, post-final, digest/size/total mismatched or over-limit chunks are rejected. Manifest verification alone is not recovery evidence: OBL-004 also requires bounded-streaming encrypted snapshot creation and restore into a fresh disposable MySQL schema, raw encrypted-chunk canary absence, and post-restore row/envelope/blind-index/checkpoint integrity.
- **Atomic admission and replay:** one transaction compares-and-sets a single Phase-owned record containing `migration_set_id`, canonical subject digest, sequence, signer version/fingerprint, writer digest, snapshot digest and pair digest only after both schemas, both signatures, the shared subject and the full chunk inventory pass. Exact re-verification of the already accepted tuple is idempotent; a split pair, cross-pair splice, individual replay, same-sequence digest change, separately accepted role, or half-written state fails closed. No lease, checkpoint, event or business-table mutation occurs unless this pair admission commits. Replay sequence is global across migration sets and anchor rotation.
- **Trust-anchor rollout:** first deploy the new fingerprint/version as `ACTIVE` and demote the old anchor to `RETIRING` with `max_sequence` equal to the globally last accepted pair sequence. Only the ACTIVE anchor may atomically admit a higher-sequence pair; RETIRING anchors may reverify only an already accepted exact pair tuple and cannot advance or change either digest. Then issue both paired signatures under the new ACTIVE key at one higher global sequence. Remove the retiring anchor only when no run/checkpoint references its accepted pair. Compromise marks the version `REVOKED`, invalidates pair state signed by it, blocks every mutating command, and requires one fresh inseparable pair under a non-revoked ACTIVE anchor.
- **Command and schemas:** `phase03-migration preflight --writer-manifest PATH --writer-signature PATH --snapshot-manifest PATH --snapshot-signature PATH --environment ID --database-instance-fingerprint HEX --schema NAME --flyway-set-digest HEX` is the only production admission command. Machine-readable JSON schemas own both manifest formats, and a checked-in CLI contract owns golden `--help`, subcommands/options and exits. Exit codes are fixed: `0` accepted, `20` invalid invocation/path, `21` canonical/schema failure, `22` signature/fingerprint/trust-anchor/pair-signature failure, `23` migration-set/environment/database/schema/Flyway mismatch, `24` empty/unknown/stale/replayed/spliced writer pair, `25` invalid/unavailable/chunk-incomplete encrypted snapshot, and `26` key/provider preflight failure. Any nonzero result precedes leases, checkpoints, events, pair admission or legacy updates and must leave every mutable count at zero.
- **Scope:** deployment/migration admission only; no secret signing key enters the repository or application.

## DR-P03-009 — Tenant evidence uses staged protected-object IDs

- **Decision:** tenant registration never accepts, fetches, or persists external evidence URLs. The fixed flow is: create an opaque registration-object session, upload each object through a multipart endpoint, then submit registration JSON containing only the session ID and five purpose-bound `pobj_v1_*` IDs. Staged objects are tenant-draft/purpose bound, single-claim, non-reusable, and atomically claimed with tenant persistence.
- **API:** `POST /api/v1/console/tenants/registration-object-sessions` returns a session ID, a session-bound upload token, and expiry marker. The same token may upload all five purposes sequentially and replace the current STAGED object for a purpose while that exact tenant-draft/session remains OPEN. After media/size validation and before encryption or object-store work, an atomic OPEN-session reservation consumes one admitted-attempt slot; at most three attempts per purpose and fifteen attempts per session are permitted, and any failure after reservation consumes its slot. Concurrent reservations cannot exceed either bound and return HTTP 429 `REGISTRATION_UPLOAD_LIMIT_REACHED`; rejected media/size input before reservation does not consume a slot. The token never crosses a session or tenant draft and becomes invalid at expiry, explicit `DELETE /api/v1/console/tenants/registration-object-sessions/{sessionId}`, successful registration claim, or any terminal close. `POST /api/v1/console/tenants/registration-object-sessions/{sessionId}/objects/{purpose}` accepts exactly one multipart part named `file` plus `X-Registration-Upload-Token`; it returns the opaque protected-object ID and purpose. `POST /api/v1/console/tenants/register` accepts the session ID and object ID fields `businessLicenseObjectId`, `legalRepIdFrontObjectId`, `legalRepIdBackObjectId`, `shortlinkDomainProofObjectId`, and `trademarkProofObjectId`; the token remains in the header and is never stored or echoed.
- **Upload-token digest contract:** the `regup_v1_` credential contains a nonsecret lookup ID plus a 32-byte secret, but uses `OpaqueTokenDigestPort` purpose `REGISTRATION_UPLOAD`, a distinct nonextractable PKCS11 HMAC alias and tenant-draft/session binding. It cannot verify in the capability domain. Issue is ACTIVE-only; stored ACTIVE/RETIRING versions verify in constant time until terminal session state. Because raw secrets are not retained, a retiring token-digest key cannot be backfilled and cannot retire until every live capability or OPEN registration session referencing that exact purpose/version is terminal; the two purpose counts are independent.
- **Object rules:** business license is required and accepts PDF/JPEG/PNG up to 10 MiB; legal-representative front/back are required and accept JPEG/PNG up to 5 MiB each; short-link-domain proof and trademark proof are optional and accept PDF/JPEG/PNG up to 10 MiB each. Server-side signature sniffing must match the declared media type. A session has at most one current STAGED object per purpose, uses configured `PT24H` expiry, and transitions objects through `STAGED -> CLAIMED` or `STAGED -> EXPIRED/ORPHANED -> DELETED`. A failed tenant transaction leaves objects staged for deterministic reconciliation; object-store success plus metadata failure is reconciled by operation ID.
- **Compatibility and errors:** legacy `*Url` JSON fields and any `http(s)` value are rejected with HTTP 422 and code `LEGACY_OBJECT_URL_NOT_ACCEPTED`; missing required IDs use `REGISTRATION_OBJECT_REQUIRED`; wrong session/purpose/tenant-draft, reused/expired ID, media mismatch, oversize, and partial claim have stable distinct 4xx codes. Unknown JSON fields fail closed. No silent legacy acceptance or remote URL fetch exists.
- **Documentation:** `core/docs/API.md` and `docs/使用手册.md` must match the runtime DTO, endpoints, media/size rules, lifecycle, error codes, and old-client rejection behavior.
- **Scope:** protected upload/storage/claim semantics for the existing endpoint only; qualification workflow, UI, RBAC, and reveal policy remain later phases.

## DR-P03-011 — Historical digest migration and snapshot recovery are explicit production paths

- **Decision:** Legacy lowercase mobile SHA-256 cells are not reversible and must never be treated as plaintext mobile numbers. The migration bridge decodes the reviewed 64-character digest, submits its 32 bytes to the same target/field/purpose/scope-bound PKCS11 HMAC input used by online lookup, and joins the result to the exact ACTIVE/RETIRING key-reference set. Snapshot chunks use the independent `SNAPSHOT_RECOVERY` alias/reference and reservation count, not the field KEK.
- **Command contract:** `phase03-migration advance` owns every `DISCOVERED -> BACKFILLED -> VERIFIED -> CUTOVER -> SCRUBBED -> COMPLETE` edge. Integration tests may compose `DefaultServices`, but may not call `runner.advance` as a substitute for the command surface.
- **Recovery contract:** MySQL dump stdout is held in at most one fixed 10 MiB plaintext buffer plus one-byte lookahead, persisted only as complete encrypted chunks, fully inventoried/authenticated before restore starts, then decrypted one bounded chunk at a time into a distinct fresh schema. Recovery completion is written only after the MySQL client succeeds.
- **Evidence:** Real MySQL/SoftHSM Plan 14 produces a strict counts/digests-only seven-target inventory; V1, target-set, state, legacy-fallback and no-index facts are independently validated.
