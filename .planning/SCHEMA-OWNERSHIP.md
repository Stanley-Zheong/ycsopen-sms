# Schema Ownership and Migration Conflict Contract

## Governing rules

This registry assigns every stable persistence domain or prefix to exactly one roadmap package. It does not invent physical tables: phase design binds a concrete table, index, event-store, cache-persistence, or object-store prefix beneath the registered logical prefix before a migration is planned.

Every record has exactly nine ` | ` separated fields:

`Schema ID | PRD data domain | Schema object/prefix | Owner package | Migration namespace | Dependencies | Compatibility | Rollback | Cross-owner protocol`

- `Schema object/prefix` is stable. Renaming or splitting it requires a recorded decision and an update to all affected schema claims.
- Migration namespaces are globally non-overlapping. A migration ID is used once across all phase claims and SQL migration files.
- Compatibility is always `expand-migrate-contract`: expand remains backward compatible, migrate is restartable and observable, and contract runs only after every reader/writer is proven compatible.
- Rollback never assumes destructive reversal. Each claim records a forward-compatible rollback, restored snapshot, or compensating migration.
- A phase changing another package's prefix keeps the registered owner in its claim and records owning-package approval as a stable `DR-*` entry in the active phase's `DECISIONS.md`.
- `.planning/tools/validate-phase-entry.rb` rejects unknown owners/dependencies, duplicate prefixes, overlapping namespaces, duplicate migration IDs, incompatible claims, missing cross-owner approval, and duplicate SQL migration versions.

## Phase schema claim contract

A phase that plans a persistence migration writes `Schema migrations: declared` in `DESIGN.md` and creates `SCHEMA-CLAIMS.md` with this exact table:

| Claim ID | Schema object/prefix | Owner package | Migration ID | Depends on migration | Compatibility step | Rollback | Cross-owner approval |
| --- | --- | --- | --- | --- | --- | --- | --- |
| SC-<NN>-001 | <registered-prefix/concrete-object> | <registered-owner> | V<unique-number> | <V IDs or -> | <expand, migrate, or contract> | <executable rollback/compensation> | <- or DR-ID present in DECISIONS.md> |

If no persistence migration is planned, `DESIGN.md` states `Schema migrations: none` and no `SCHEMA-CLAIMS.md` is created. Schema approval is planning authority only; executed migration tests, compatibility evidence, rollback evidence, TODO-empty proof, review, and remote commit gates still apply.
