# PRD Atomic Obligation Catalog

## Purpose and authority

This catalog atomizes the normative content of `docs/PRD.md` so that a coarse requirement group cannot be declared complete while one of its page, field, transition, failure, permission, data, flow, or acceptance obligations remains unproved.

The stable identity is the `OBL-*` value. `Owner package` is the only implementation owner and intentionally uses a package ID rather than a phase number. The roadmap may renumber phases without changing this catalog. A planned reference is not completion evidence; an obligation closes only when its owning phase records an executed result at the stated evidence target and the authoritative TODO query has no unchecked scoped item.

## Machine-readable record law

Every catalog record is one Markdown line with exactly nine fields separated by ` | `:

`Obligation ID | Source | Requirement IDs | Owner package | Planned behavior ID | UI reference | Test ID/layer | Evidence target | Atomic obligation`

- `Obligation ID` is globally unique and immutable.
- `Requirement IDs` is a nonempty comma-separated list without spaces. Every `F-x.y` token in `Source` maps mechanically to `REQ-F-x-y`; NFR obligations map semantically to the nine stable `REQ-NFR-*` IDs in `REQUIREMENTS.md`.
- Obligations without a direct top-level requirement use one or more IDs from the registered `PROJECT-*` namespace below. A `PROJECT-*` ID is planning authority, not a substitute for a matching `REQ-*` trace when the source names a functional requirement.
- `Owner package` contains exactly one package ID from the approved phase-package vocabulary.
- `Planned behavior ID` follows `<package-id>-<number>` and is bound into the phase SPEC.
- UI references use `page:<page-id>` for route-level inventory and `element:<data-testid>` for an asserted element. Element values match `^(admin|tenant|shared|public)-[a-z0-9]+-[a-z0-9]+-[a-z0-9]+-[a-z0-9]+(?:-[a-z0-9]+)*$`. `-` means no direct UI surface.
- Test references use `<test-id>:<layer>`. Allowed layers are `static`, `unit`, `component`, `integration`, `database`, `api`, `protocol`, `security`, `accessibility`, `visual`, `playwright`, `load`, `fault`, and `uat`.
- Evidence targets are phase-relative and become `.planning/phases/<NN>-<owner-package>/EVIDENCE/<OBL-ID>.json` unless a more specific extension is named.
- A source may cite several PRD clauses when they form one indivisible cross-module obligation; the record still has one owner.

### Registered project requirement namespace

- PROJECT-PLANNING-TRACE: executable planning, traceability, review, TODO-empty, and remote evidence contracts.
- PROJECT-UI-CONTRACT: shared route, manifest, selector, accessibility, responsive, and UI-state contracts.
- PROJECT-ADMIN-IA: complete Admin portal information architecture without a direct top-level functional ID.
- PROJECT-TENANT-IA: complete Tenant portal information architecture without a direct top-level functional ID.
- PROJECT-SYSTEM-CONFIG: production system-configuration management surface and behavior.
- PROJECT-TENANT-HELP: production tenant guide, API documentation, and customer-service help center.
- PROJECT-SYSTEM-MESSAGING: shared system-message delivery and notification bootstrap behavior.
- PROJECT-FIELD-CONTRACT: normative field, validation, and form semantics.
- PROJECT-STATE-MACHINE: normative entity and job state transitions.
- PROJECT-EXCEPTION-FLOW: cross-module exception and degraded-path behavior.
- PROJECT-CHAPTER-12-FLOW: PRD chapter 12 end-to-end lifecycle and operations flows.
- PROJECT-PROTOCOL-ACCEPTANCE: real-provider HTTP/CMPP and cross-protocol acceptance composition.
- PROJECT-DOD: definition-of-done and final release composition obligations.
- PROJECT-DATA-MODEL: normative persistent data shape and integrity constraints.
- PROJECT-PERMISSION-CONTRACT: cross-cutting permission and data-scope enforcement.
- PROJECT-DISPLAY-CONTRACT: cross-cutting masking, metric provenance, and accessible display rules.
- PROJECT-EVENT-REGISTRY: required business-event registry and correlation contract.
- PROJECT-TERMINATION-COMPOSITION: complete termination participant inventory and irreversible closure contract.
- PROJECT-PROVIDER-STATUS-TAXONOMY: one effective provider status taxonomy shared by every producer and consumer.

```sh
ruby .planning/tools/validate-prd-obligations.rb
ruby .planning/tools/validate-prd-obligations.rb --assert-unique --assert-traced
ruby .planning/tools/validate-prd-obligations.rb --owner secure-http-message-acceptance

ruby .planning/tools/validate-prd-obligations.rb --id-prefix OBL-ACCEPT-
ruby .planning/tools/test-bootstrap-phase-01.rb
```

The validator checks all 522 records even when a selector limits the reported selection. It enforces nine fields, mandatory values, known owners, owner-prefixed behaviors, known and nonduplicated requirement links, 108/108 requirement coverage, allowed test layers, evidence syntax, full element `data-testid` syntax, global uniqueness of obligation/test/evidence identities, and the rule that every direct `page:` or `element:` owner is a roadmap UI phase with the UI entry gate.

The bootstrap self-test builds a complete temporary Phase 1 fixture, requires it to pass, then injects a catalog-known foreign obligation into SPEC, TODO, and TEST-MATRIX and requires all three files to fail with `FOREIGN_OBLIGATION_ID`.
