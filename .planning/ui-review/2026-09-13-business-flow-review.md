# 页面与业务闭环复核

复核方式：使用 Chrome 152 + Playwright CDP 登录测试环境 `127.0.0.1:19089`，遍历 admin 菜单页面，检查可见字段、按钮、表格、空状态，并对机构管理页面读取实际 API 返回数据。

## 已确认的问题

### P1 机构状态动作未覆盖所有机构

`GET /api/v1/console/admin/tenants` 返回两条机构：`DEV-TENANT` 与 `DEMO-001`。页面第一行只有“审核/编辑”，第二行才有“账户状态”。代码以 `accountRevision !== null` 隐藏按钮，导致尚未开户的机构无法从机构列表进入状态管理。若业务规则是不允许未开户机构变更状态，应显示禁用按钮和原因，而不是让操作列缺少动作。

建议：每行固定渲染“审核、编辑、账户状态”；未满足前置条件时按钮 disabled，并以 tooltip/辅助文案说明“尚未开户，不能变更运行状态”。

### P1 告警解决/静音指令缺少上下文

告警页把“解决原因”“静音原因”放在历史列表上方，当前没有选中的告警。解决/静音实际在表格行按钮上提交，但原因输入与具体告警没有绑定；“保存规则”和“模拟源事件评估”也并列在同一表单，用户无法从界面判断一个是持久化配置、一个是测试指令。

建议：将解决/静音原因放入对应告警行的确认弹窗，弹窗展示告警标题、当前状态、影响范围和将要调用的指令；将“模拟源事件评估”移到独立的“测试规则”区域并明确不会替代真实事件。

### P1 操作原因输入框的指令边界不清

充值审核、上行明细重放、详单动作、推送失败、发送任务检索等页面均存在独立的原因输入框。它们最终被行级通过/拒绝/重放/暂停等 mutation 使用，但页面没有在输入框附近说明“该原因将用于下一次操作”，空列表时输入框仍然显示，容易误认为是查询条件。

建议：把原因字段移动到行操作确认弹窗；或在字段旁明确显示“用于下一次 X 操作”，并在没有可操作记录时禁用。提交请求和成功/失败反馈必须带同一条记录 ID，便于闭环追踪。

### P2 查询数据流虽可用，但控件与动作表达不统一

机构管理页查询会请求 `/api/v1/console/admin/tenants` 并刷新结果；上行页同时有明细查询和推送监控查询，两个 QueryPanel 使用相同的 `query-submit/query-reset` test-id，自动化和用户理解都容易混淆。部分空列表仍显示操作原因或无结果区动作。

建议：为每个业务区使用带领域前缀的 test-id 和按钮文案（如“查询上行明细”“查询推送失败”），并在空状态中说明下一步动作；同页多个查询区必须分别显示请求范围和结果区域。

### P2 QueryPanel 仍以三列为默认布局

`QueryPanel` 的默认网格是 `repeat(3, minmax(260px, 1fr))`，与项目规范“一行最多四个组件”的要求不一致。部分页面通过独立 CSS 覆盖后出现 5 个超宽控件，说明布局契约没有收敛到一个组件规则。

建议：统一由 QueryPanel 控制四列/响应式断点，页面样式只提供例外；为每个查询区增加列数、控件宽度和动作右对齐的 Playwright 几何断言。

## 已确认的闭环

- 机构查询：输入条件 → QueryPanel submit → 更新 applied filters → 请求 tenants → 表格刷新，链路闭合。
- 充值审核：列表查询 → 行级通过/拒绝 → mutation → 成功消息 → invalidate 查询，链路闭合，但原因字段上下文需收紧。
- 上行重放：行级重放 → `replayAdminUplink(id, reason)` → 成功消息 → 刷新明细和推送监控，链路闭合。
- 告警：规则保存和源事件评估均有 mutation 与刷新，但测试指令和生产指令混在同一视觉区域，解决/静音原因缺少选中告警上下文。

## 建议的修改顺序

1. 先修复机构列表每行操作列的一致性和禁用原因（Issue #90）。
2. 再将告警解决/静音、充值/重放等原因输入改为行级确认上下文（Issue #91、#92）。
3. 最后收敛 QueryPanel 四列布局、领域化 test-id 和空状态动作表达（Issue #89、#87、#88）。
