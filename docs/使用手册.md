# YCSOpen SMS 安装、部署与配置使用手册

本文面向需要从源码运行、部署或维护 YCSOpen SMS 的开发者和运维人员。内容以当前仓库代码、
`application*.yml`、Maven/NPM 脚本和 Flyway migration 为准。

> 当前仓库包含真实功能、简化实现和占位模块，不是可直接暴露到公网的生产成品。控制台 JWT
> 请求过滤、开放 API 完整 HMAC 验签、Redis nonce 防重放、真实通道交付等仍有未完成项。部署前请先读
> [`core/docs/ROADMAP.md`](../core/docs/ROADMAP.md) 与
> [`web/docs/ROADMAP.md`](../web/docs/ROADMAP.md)。

## 系统组成

```text
浏览器
  │  http://localhost:5173（开发）或 Nginx（部署）
  ├── React 18 + Vite 静态应用
  │       │ /api/*
  │       ▼
  └── Spring Boot :8080
          ├── MySQL 8 :3306（Flyway 建表）
          └── Redis :6379（频控与限流计数）
```

后端与前端是两个独立构建单元：

- `core/`：Java 21、Spring Boot 3.3、Maven、MySQL、Redis。
- `web/`：Node.js 20+、React 18、TypeScript、Vite。
- 开发环境由 Vite 把 `/api` 转发到 `http://localhost:8080`。
- 部署环境建议由 Nginx 提供前端静态文件，并以同域 `/api/` 反向代理后端。

## 准备 MySQL 和 Redis

### 方式一：使用本机服务

启动本机 MySQL 8 和 Redis，然后验证：

```bash
mysql -u root -e "SELECT VERSION();"
redis-cli ping
```

Redis 应返回 `PONG`。

### 方式二：只用容器运行依赖

项目当前没有 Dockerfile 或 Compose 文件，但可用容器提供 MySQL/Redis：

```bash
docker run -d \
  --name ycsopen-mysql \
  -e MYSQL_ROOT_PASSWORD=local-root-password \
  -p 3306:3306 \
  mysql:8.0 \
  --character-set-server=utf8mb4 \
  --collation-server=utf8mb4_unicode_ci

docker run -d \
  --name ycsopen-redis \
  -p 6379:6379 \
  redis:7-alpine
```

确认依赖已就绪：

```bash
docker exec ycsopen-mysql mysqladmin ping -uroot -plocal-root-password
docker exec ycsopen-redis redis-cli ping
```

## 初始化数据库

### 本机 root 可免密登录

仓库脚本会创建数据库和应用账号，表结构由应用启动时的 Flyway 自动创建：

```bash
cd core
./tools/init-db.sh
```

脚本默认值：

| 项目 | 默认值 |
|---|---|
| 数据库 | `ycsopen_sms` |
| 数据库用户 | `ycsopen` |
| 数据库密码 | `ycsopen` |
| 字符集/排序规则 | `utf8mb4` / `utf8mb4_unicode_ci` |

也可以传入自定义值：

```bash
./tools/init-db.sh <database> <username> <password>
```

### root 需要密码或 MySQL 在容器中

先用有建库/授权权限的账号进入 MySQL：

```bash
mysql -h 127.0.0.1 -P 3306 -u root -p
```

执行：

```sql
CREATE DATABASE IF NOT EXISTS ycsopen_sms
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;

CREATE USER IF NOT EXISTS 'ycsopen'@'%' IDENTIFIED BY 'ycsopen';
GRANT ALL PRIVILEGES ON ycsopen_sms.* TO 'ycsopen'@'%';
FLUSH PRIVILEGES;
```

`ycsopen/ycsopen` 仅为源码开发默认值。对外部署时必须替换，并同步设置后端的 `DB_USERNAME`、
`DB_PASSWORD`。

## 配置后端

### 生成开发密钥

`application.yml` 内的字段加密默认值只是占位符，不是可用 AES 密钥。启动后端前必须设置：

```bash
export JWT_SECRET="$(openssl rand -base64 48 | tr -d '\n')"
export FIELD_ENCRYPTION_KEY="$(openssl rand -base64 32 | tr -d '\n')"
```

- `JWT_SECRET` 用于签发控制台 JWT。
- `FIELD_ENCRYPTION_KEY` 必须是 Base64 编码的 32 字节 AES 密钥。
- 命令每次都会生成新值。已加密数据存在后不能随意更换字段密钥，否则旧数据无法解密。
- 不要把真实密钥写入 Git、README、启动脚本或 systemd unit；使用权限受控的环境文件或 KMS。

### 配置参考

| 环境变量 | 开发默认值 | 作用与约束 |
|---|---|---|
| `SPRING_PROFILES_ACTIVE` | `dev` | `application.yml` 当前默认激活 `dev` |
| `SPRING_DATASOURCE_URL` | `jdbc:mysql://localhost:3306/ycsopen_sms?...` | 覆盖完整 JDBC URL |
| `DB_USERNAME` | `ycsopen` | `application-dev.yml` 数据库用户 |
| `DB_PASSWORD` | `ycsopen` | `application-dev.yml` 数据库密码 |
| `REDIS_HOST` | `localhost` | Redis 主机 |
| `REDIS_PORT` | `6379` | Redis 端口 |
| `SERVER_PORT` | `8080` | Spring Boot HTTP 端口 |
| `JWT_SECRET` | 不安全占位值 | 至少使用足够强的随机值；部署时必须显式设置 |
| `FIELD_ENCRYPTION_KEY` | 不可用占位值 | Base64 编码的 32 字节 AES 密钥；启动前必须设置 |
| `YCSOPEN_SECURITY_JWT_ACCESS_TOKEN_TTL_MINUTES` | `120` | 控制台访问令牌有效期 |
| `YCSOPEN_ROUTING_COMPLAINT_RATIO_THRESHOLD` | `0.003` | 投诉占比阈值 |
| `YCSOPEN_THIRD_PARTY_BLACKLIST_ENABLED` | `false` | 是否启用第三方黑名单查询 |
| `THIRD_PARTY_BLACKLIST_URL` | 空 | 第三方黑名单基础 URL |
| `THIRD_PARTY_BLACKLIST_APP_ID` | 空 | 配置预留；当前客户端尚未实际消费该值 |

第三方黑名单还支持 Spring relaxed binding 覆盖：

- `YCSOPEN_THIRD_PARTY_BLACKLIST_TIMEOUT_MS`，默认 `800`。
- `YCSOPEN_THIRD_PARTY_BLACKLIST_FAIL_OPEN`，默认 `true`。

```sql
INSERT INTO users (
  username,
  password_hash,
  real_name,
  user_type,

  failed_login_count,
  created_by

  '$2a$10$Zfn0WBm0FBiNkDFuGgsZv.OnOUL8sBR7GdvZTEtgh9O4ssEA6QQe2',
```

## 部署后端 JAR

下面示例使用 Linux、systemd 和 `/opt/ycsopen-sms`。先创建受限用户并放置 JAR：

```bash
sudo useradd --system --home /opt/ycsopen-sms --shell /usr/sbin/nologin ycsopen-sms
sudo install -d -o ycsopen-sms -g ycsopen-sms /opt/ycsopen-sms/core
sudo install -m 0644 core/target/ycsopen-sms-core.jar /opt/ycsopen-sms/core/
sudo install -d -m 0750 /etc/ycsopen-sms
```

创建 `/etc/ycsopen-sms/core.env`，把占位值替换为部署环境的真实值：

```ini
SPRING_PROFILES_ACTIVE=dev
SPRING_DATASOURCE_URL=jdbc:mysql://mysql.example.com:3306/ycsopen_sms?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai&useSSL=true
DB_USERNAME=<database-user>
DB_PASSWORD=<database-password>
REDIS_HOST=redis.example.com
REDIS_PORT=6379
JWT_SECRET=<random-jwt-secret>
FIELD_ENCRYPTION_KEY=<base64-encoded-32-byte-key>
SERVER_PORT=8080
```

限制文件权限：

```bash
sudo chown root:ycsopen-sms /etc/ycsopen-sms/core.env
sudo chmod 0640 /etc/ycsopen-sms/core.env
```

创建 `/etc/systemd/system/ycsopen-sms-core.service`：

```ini
[Unit]
Description=YCSOpen SMS Core
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=ycsopen-sms
Group=ycsopen-sms
WorkingDirectory=/opt/ycsopen-sms/core
EnvironmentFile=/etc/ycsopen-sms/core.env
ExecStart=/usr/bin/java -jar /opt/ycsopen-sms/core/ycsopen-sms-core.jar
Restart=on-failure
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true

[Install]
WantedBy=multi-user.target
```

加载并启动：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now ycsopen-sms-core
sudo systemctl status ycsopen-sms-core
curl -fsS http://127.0.0.1:8080/actuator/health
```

查看日志：

```bash
journalctl -u ycsopen-sms-core -f
```

> 当前仓库没有独立 `prod` profile。上述部署显式使用 `dev` 配置并通过环境变量覆盖连接和密钥，
> 只能作为受控验证部署模板。完成生产安全门禁前，不要将服务暴露到公网。

## 部署前端与 Nginx

复制静态产物：

```bash
sudo install -d /var/www/ycsopen-sms
sudo cp -R web/dist/. /var/www/ycsopen-sms/
```

创建 Nginx server 配置：

```nginx
server {
    listen 80;
    server_name sms.example.com;

    root /var/www/ycsopen-sms;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

`try_files ... /index.html` 是 React Router 刷新子路径时不返回 404 的关键。验证配置并重载：

```bash
sudo nginx -t
sudo systemctl reload nginx
```

正式环境应在 Nginx 配置 TLS 证书，只开放 80/443，并让 MySQL、Redis、8080 仅在受控网络可达。

### 上传机构注册证明材料

注册证明材料使用私有暂存会话，不使用外部 URL。固定顺序如下：

1. `POST /api/v1/console/tenants/registration-object-sessions` 创建会话。保存响应中的
   `registrationObjectSessionId`、一次返回的 `regup_v1_` 凭据和 `expiresAt`；不要记录或持久化
   完整凭据。
2. 对每个用途调用
   `POST /api/v1/console/tenants/registration-object-sessions/{sessionId}/objects/{purpose}`。
   请求头必须是 `X-Registration-Upload-Token`，正文必须是 `multipart/form-data`，且只能包含一个
   名为 `file` 的文件 part。
3. 注册 JSON 只提交 `registrationObjectSessionId` 与对象 ID 字段
   `businessLicenseObjectId`、`legalRepIdFrontObjectId`、`legalRepIdBackObjectId`、
   `shortlinkDomainProofObjectId`、`trademarkProofObjectId`。
4. 不再继续注册时，用
   `DELETE /api/v1/console/tenants/registration-object-sessions/{sessionId}` 显式关闭会话，并携带
   同一个 `X-Registration-Upload-Token`。

用途与限制必须严格匹配：

| `{purpose}` | 必填性 | 允许媒体 | 最大明文字节 | 最大完整 YCSE/v1 信封字节 |
|---|---|---|---:|---:|
| `business-license` | 必填 | PDF/JPEG/PNG | 10,485,760 | 10,485,905 |
| `legal-rep-id-front` | 必填 | JPEG/PNG | 5,242,880 | 5,243,025 |
| `legal-rep-id-back` | 必填 | JPEG/PNG | 5,242,880 | 5,243,025 |
| `shortlink-domain-proof` | 可选 | PDF/JPEG/PNG | 10,485,760 | 10,485,905 |
| `trademark-proof` | 可选 | PDF/JPEG/PNG | 10,485,760 | 10,485,905 |

服务端同时校验声明媒体、实际签名字节、明文上限和完整信封上限。会话 TTL 固定为 `PT24H`，状态为
`OPEN -> CLAIMED | CLOSED | EXPIRED`。同一会话凭据可以在 `OPEN` 内顺序上传全部五种用途，也可以
替换同一用途当前的 `STAGED` 对象；它不能跨 session 或 tenant-draft。claim、close、expiry 后均不能
继续使用。

每个 purpose 最多预留 3 次 admitted attempt，每个 session 最多 15 次。预留发生在媒体、大小和
签名检查之后、加密和私有存储之前；并发请求不会超过任一上限。预留后的 provider、store、元数据或
reconciliation 失败会烧掉 slot。达到上限固定返回 HTTP 429
`REGISTRATION_UPLOAD_LIMIT_REACHED`。

`regup_v1_` 由非秘密 lookup ID 和 32 字节随机 secret 构成。服务端只保存 `REGISTRATION_UPLOAD`
用途、tenant-draft/session 绑定的版本化摘要；新签发只用 ACTIVE，验证接受存储的 ACTIVE/RETIRING
版本并使用常量时间比较。未知、RETIRED、REVOKED 或 `OBJECT_CAPABILITY` 跨域凭据失败关闭。

旧 `*Url` 字段和任何 HTTP(S) 形态的值不再兼容，固定返回 HTTP 422
`LEGACY_OBJECT_URL_NOT_ACCEPTED`；缺少必填对象返回 `REGISTRATION_OBJECT_REQUIRED`。上传接口的
稳定错误为 `REGISTRATION_UPLOAD_INPUT_INVALID`、`REGISTRATION_UPLOAD_TOKEN_INVALID`、
`REGISTRATION_UPLOAD_SESSION_NOT_OPEN`、`REGISTRATION_UPLOAD_SESSION_EXPIRED`、
`REGISTRATION_UPLOAD_MEDIA_TYPE_NOT_ACCEPTED`、`REGISTRATION_UPLOAD_SIZE_LIMIT_EXCEEDED`、
`REGISTRATION_UPLOAD_SIGNATURE_MISMATCH`、`REGISTRATION_UPLOAD_LIMIT_REACHED`、
`REGISTRATION_UPLOAD_UNAVAILABLE`。响应只返回 `pobj_v1_*`、purpose 和 expiry；不会返回或接收
bucket、key、public reference、presigned reference，也不会泄漏完整 token、存储定位或 provider 细节。

## Phase 3 加密迁移与快照命令

`phase03-migration` 是显式运维命令，不会随应用启动自动执行。除 `--help` 外，命令启动前必须同时提供：

- `YCSOPEN_PHASE03_MIGRATION_CONFIG`：字节级 canonical JSON 配置的绝对路径；
- `YCSOPEN_PHASE03_MIGRATION_CONFIG_SIGNATURE`：配置的 canonical Base64 Ed25519 detached signature 文件；
- `YCSOPEN_PHASE03_MIGRATION_CONFIG_PUBLIC_KEY`：由进程启动环境独立固定的 Ed25519 X.509 DER 公钥 Base64，不能从配置文件自举；
- `YCSOPEN_ENCRYPTED_SNAPSHOT_STORE_ROOT`：已有、非符号链接的私有目录；必须与签名配置中的 `snapshot.storeRoot` 解析成同一个 canonical 路径。

签名配置只保存凭据环境变量名，不保存密码或 PIN。其 `snapshot.mysqldumpPath`、
`snapshot.mysqlPath` 必须是 raw canonical、全路径无符号链接的本机可执行文件；
`snapshot.mysqldumpSha256`、`snapshot.mysqlSha256` 必须分别填写对应文件的
`sha256:<64位小写十六进制>`。可执行文件只能位于代码固定的 `/usr/bin` 或
`/opt/ycsopen/mysql-client` 受信根下，不接受 Homebrew、`/usr/local`、临时目录、snapshot/config/data
目录或另一个可配置根。服务必须以非 root 身份运行：effective UID 和 real UID 分别通过 root-owned 固定工具
`/usr/bin/id -u` 与 `/usr/bin/id -ru` 获取；任一 UID 为 `0` 或两者不相等都拒绝。两个 probe 只接受有界、单行、无前导零的
十进制结果；超时、输出超限、stderr、非零退出或格式异常均失败关闭。在组合时和每次读取
`Database.password()` 之前，
进程都会对 leaf 与全部 ancestor 执行 `NOFOLLOW_LINKS`、raw-canonical、root uid/gid、非 group/other 可写、
无 ACL、leaf regular/executable、有界长度、inode 和签名 SHA-256 检查。ACL 不依赖可选的 Java attribute view：
macOS 固定执行 `/bin/ls -lde -- <path>` 并拒绝权限 `+`/任何 ACL entry，Linux 固定执行
`/usr/bin/ls -ldn -- <path>` 并拒绝 `+`；未知 OS、未知输出、超时、超限、stderr 或非零退出全部失败关闭。
`id`/`ls` helper 启动时也清空继承环境，仅保留 `LC_ALL=C`、`LANG=C`且不接触凭据。执行文件 authority
验证在 HSM session 打开前完成。`ProcessBuilder` 启动 MySQL 客户端前清空继承环境，只注入
`MYSQL_PWD`、`LC_ALL=C`、`LANG=C`、`TZ=UTC`，不继承 `PATH/HOME/TMPDIR/LD*/DYLD*/MYSQL_HOME/LIBMYSQL_PLUGIN_DIR`。
配置签名覆盖：

```text
ASCII("YCS-PHASE03-PRODUCTION-CONFIG-SIGNATURE/v1\0")
|| u32be(canonical_config_byte_length)
|| exact_canonical_config_bytes
```

非 canonical JSON、坏签名、错误公钥、缺少任一启动输入、可写的不可信路径、符号链接或根目录不一致都会在连接
MySQL/HSM 前失败。私钥必须保留在离线发布系统，不得放入仓库或部署主机配置。

该执行边界信任 root 管理员和不可变部署镜像对上述两个受信根的管理。威胁模型允许攻击者写 snapshot、config
或 data 目录，但攻击者不能提权、ptrace 服务进程、mount 覆盖受信根或获得 root；root/部署镜像已被攻破不在该边界内。

签名配置中的 JDBC 账号是快照操作账号：必须能够读取源 schema，并能够在运维人员预先创建的目标空 schema
中建表和写入数据。命令不会替账号扩权，也不会自动创建或清空目标 schema；仅有源库权限的普通应用账号不能用于
`snapshot-restore`。恢复目标必须是本次恢复专用且独占的 schema，从 fresh-schema 检查开始到完成后的校验结束不得有
其他写入者。建议为该账号设置短期凭据，并在恢复完成后立即撤销目标库写权限。

快照操作的固定命令为：

```bash
phase03-migration snapshot-create \
  --snapshot-id <id> --environment <id> \
  --database-instance-fingerprint <64-hex> --schema <source-schema> \
  --flyway-set-digest <64-hex> --global-sequence <nonnegative-decimal> \
  --signer-key-version <version>

phase03-migration snapshot-restore \
  --snapshot-id <id> --pair-digest <64-hex> --target-schema <fresh-schema>

phase03-migration snapshot-delete \
  --snapshot-id <id> --snapshot-digest <64-hex>
```

`snapshot-create` 只使用数据库中唯一可写的 `SNAPSHOT_RECOVERY` 密钥引用，并通过固定 argv 的
`mysqldump` 直接流入加密分块，不产生明文 dump 文件。创建后需离线签署 writer/snapshot manifest pair，再执行
`preflight`；生产 preflight 会在数据库 CAS 之前，从同一个 FileStore 验证精确 manifest、全部分块摘要和逐块解密
认证。`snapshot-restore` 只从该 FileStore 取 manifest，并要求数据库当前 accepted pair 精确匹配；目标 schema
必须事先创建、不同于源 schema 且没有任何表。`snapshot-delete` 不依赖会被后续 admission 替换的 current pair，
但必须提供 retained canonical manifest 的精确 SHA-256 digest。全局序列从 `0` 开始合法，创建、签名 pair、数据库
admission 和恢复使用同一个非负整数契约。

创建快照和校验恢复目标使用同一套确定性 dump profile：`--no-defaults`、`--skip-opt`，随后显式启用
`--create-options --set-charset --quote-names --triggers --complete-insert --order-by-primary --hex-blob`，并禁用
add-drop-table、locks、disable-keys、extended-insert、comments 和 dump-date；字符集固定为 `utf8mb4`，时区为 UTC，
进程环境固定 `LC_ALL=C`、`TZ=UTC`。源与恢复目标的所有基础表必须使用 InnoDB；业务表必须存在稳定的非空唯一顺序，
routine/event 数量必须为零。view 不作为基础表导出，trigger 按上述 profile 导出。

恢复完成标记只是快速提示，不是当前数据库正确性的证据。首次恢复在写标记之前、重复恢复在返回
`already_complete` 之前，都会重新认证 retained manifest/全部加密分块，并将解密 SQL 的有界流式
`(byte length, SHA-256)` 与目标 schema 使用同一 profile 实时重导出的结果比较；目标被删除、被改写或 retained chunk
缺失/损坏时都返回 `25`，且不会写入或信任完成标记。完成标记按 snapshot ID 独立目录存放，删除 `a` 不会删除
`a.b` 的恢复状态；两个 target 并发首次发布同一 snapshot 的完成标记时，独立目录创建也使用精确的
create-or-revalidate 合约，不会将合法的同时创建误判为恢复失败。

命令只输出无敏感信息的单行 JSON。快照缺失、分块不完整、摘要/认证失败、非 fresh schema 等固定使用退出码
`25`；key/provider 不可用使用 `26`。完整选项与退出码以
`core/src/main/resources/security/migration/phase03-migration-cli-contract.json` 和 `--help` 为准。

## 停止服务

开发模式在对应终端按 `Ctrl+C`。systemd 部署使用：

```bash
sudo systemctl stop ycsopen-sms-core
```

容器依赖使用：

```bash
docker stop ycsopen-mysql ycsopen-redis
```

## 升级

升级前先备份数据库和部署环境的密钥/配置。不要把密钥备份进源码目录。

```bash
mysqldump -h <mysql-host> -u <backup-user> -p \
  --single-transaction ycsopen_sms > ycsopen_sms-backup.sql

git pull --ff-only

cd core
mvn test
mvn clean package

cd ../web
npm ci
npm test
npm run build
```

随后替换 JAR 和 `web/dist/`，重启后端，验证健康检查和登录。应用启动时 Flyway 会执行尚未应用的
migration；若 Flyway validation 失败，不要删除历史记录强行继续，应核对 migration 是否被改写。

## 故障排查

### 后端启动时报字段密钥/Base64 错误

原因：未设置 `FIELD_ENCRYPTION_KEY`，或值解码后不是合法 AES 密钥长度。

```bash
export FIELD_ENCRYPTION_KEY="$(openssl rand -base64 32 | tr -d '\n')"
```

已有加密数据时必须恢复原密钥，不能生成新值代替。

### JWT 报 weak key

原因：`JWT_SECRET` 长度不足。

```bash
export JWT_SECRET="$(openssl rand -base64 48 | tr -d '\n')"
```

### MySQL `Access denied`

检查实际主机、端口、账号授权和环境变量：

```bash
mysql -h 127.0.0.1 -u ycsopen -p ycsopen_sms
env | grep -E 'SPRING_DATASOURCE_URL|DB_USERNAME|DB_PASSWORD'
```

不要把上述 `env` 输出粘贴到公开 issue，它可能包含密码。

### Redis 连接失败

```bash
redis-cli -h "${REDIS_HOST:-localhost}" -p "${REDIS_PORT:-6379}" ping
```

确认返回 `PONG`，并检查防火墙、认证和容器端口映射。

### Web 登录提示用户名或密码错误

- 确认已执行管理员初始化 SQL。
- 确认后端健康检查通过。
- 检查浏览器 Network 中 `/api/v1/console/auth/login` 的响应。
- 连续错误达到 5 次后，按本文 SQL 将账号恢复为 `ACTIVE` 并清零失败次数。

### 前端调用到了错误的后端

开发环境的代理固定在 [`web/vite.config.ts`](../web/vite.config.ts) 中，目标是
`http://localhost:8080`。后端改端口后必须同步修改代理，或继续让 Nginx 提供同源 `/api/`。

### 刷新前端子页面返回 404

Nginx 缺少 SPA fallback。确认 `location /` 中有：

```nginx
try_files $uri $uri/ /index.html;
```

### Flyway validation 失败

不要修改已经执行过的 migration。比较数据库 `flyway_schema_history` 与
`core/src/main/resources/db/migration/`，新增一个更高版本 migration 完成修正。
