# YCSOpen SMS 安装、部署与配置使用手册

本文面向需要从源码运行、部署或维护 YCSOpen SMS 的开发者和运维人员。内容以当前仓库代码、
`application*.yml`、Maven/NPM 脚本和 Flyway migration 为准。

> 当前仓库包含真实功能、简化实现和占位模块，不是可直接暴露到公网的生产成品。控制台 JWT
> 请求过滤、真实通道交付等仍有未完成项。HTTP 开放 API 已具备完整 HMAC 验签、Redis nonce 防重放、
> IP 白名单和业务幂等接入边界。部署前请先读
> [`core/docs/ROADMAP.md`](../core/docs/ROADMAP.md) 与
> [`web/docs/ROADMAP.md`](../web/docs/ROADMAP.md)。

## 系统组成

```text
浏览器
  │  http://localhost:5173（开发）或 Nginx（部署）
  ├── React 18 + Vite 静态应用
  │       │ /api/*
  │       ▼
  └── Spring Boot :8080
          ├── MySQL 8 :3306（Flyway 建表）
          └── Redis :6379（频控与限流计数）
```

后端与前端是两个独立构建单元：

- `core/`：Java 21、Spring Boot 3.3、Maven、MySQL、Redis。
- `web/`：Node.js 20+、React 18、TypeScript、Vite。
- 开发环境由 Vite 把 `/api` 转发到 `http://localhost:8080`。
- 部署环境建议由 Nginx 提供前端静态文件，并以同域 `/api/` 反向代理后端。

## 准备 MySQL 和 Redis

### 方式一：使用本机服务

启动本机 MySQL 8 和 Redis，然后验证：

```bash
mysql -u root -e "SELECT VERSION();"
redis-cli ping
```

Redis 应返回 `PONG`。

### 方式二：只用容器运行依赖

项目根目录提供完整 Docker Compose 栈；如只想启动依赖，也可以使用下面两个容器：

```bash
docker run -d \
  --name ycsopen-mysql \
  -e MYSQL_ROOT_PASSWORD=local-root-password \
  -p 3306:3306 \
  mysql:8.0 \
  --character-set-server=utf8mb4 \
  --collation-server=utf8mb4_unicode_ci \
  --log-bin-trust-function-creators=ON

docker run -d \
  --name ycsopen-redis \
  -p 6379:6379 \
  redis:7-alpine
```

确认依赖已就绪：

```bash
docker exec ycsopen-mysql mysqladmin ping -uroot -plocal-root-password
docker exec ycsopen-redis redis-cli ping
```

### 方式三：启动完整本地演示栈

```bash
mvn -f core/pom.xml -DskipTests package
npm --prefix web ci && npm --prefix web run build
docker compose up --build
```

打开 <http://localhost:8088/login>，使用 `admin / Admin@123456` 登录。演示机构编号为 `DEMO-001`，
包含已审核签名、验证码模板、初始余额和 Sandbox HTTP 通道。清除容器和数据库数据：
`docker compose down -v`。这些凭据和数据只用于本机开发，禁止用于生产。

`log_bin_trust_function_creators` 允许无 `SUPER` 权限的 Flyway 迁移账号创建用于保护审计记录不可更改的触发器和终态过程。
这是 V1500 的强制迁移前置条件：当 `@@GLOBAL.log_bin=1` 时，`@@GLOBAL.log_bin_trust_function_creators` 必须为 `1`。
迁移前执行 `SELECT @@GLOBAL.log_bin, @@GLOBAL.log_bin_trust_function_creators;`；若结果为 `1,0`，应由数据库管理员通过
配置文件或托管数据库参数组启用该变量后再启动 Flyway，不要给应用账号或迁移账号追加 `SUPER` 权限。
应用内 Flyway callback 与 `init-db.sh` 都会提前检查并给出明确错误，避免在 V1500 中途以 MySQL 1419 失败。

## HTTP 单条发送 API

入口：`POST /api/v1/sms/send`

必需鉴权头：

- `X-App-Key`
- `X-Timestamp`：Unix 秒，允许 5 分钟偏差。
- `X-Nonce`：同一 API Key 下 5 分钟内不可复用。
- `X-Signature`：`Base64(HMAC-SHA256(stringToSign, appSecret))`。

`stringToSign` 拼接规则：

```text
HTTPMethod
URI
QueryString
x-app-key:{X-App-Key}
x-nonce:{X-Nonce}
x-timestamp:{X-Timestamp}
Body
```

请求体字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| `submitId` | 是 | 调用方业务流水号；同一机构重复提交相同 `submitId` 和相同内容时返回原消息结果，不重复建任务或扣费。 |
| `phoneNumber` | 是 | 国内手机号，必须匹配 `^1[3-9]\\d{9}$`。 |
| `templateId` | 是 | 本机构已审核通过的模板 ID。 |
| `signId` | 否 | 签名 ID；模板存在有效默认签名时可省略。 |
| `templateParams` | 按模板 | 必须与模板变量完全一致，不能缺失或多传。 |
| `callbackUrl` | 否 | HTTPS 回调地址。 |

通过验签、限流、租户准入、模板签名合规、路由和计费预扣后，接口返回统一结构中的 `data.messageId`。
受理成功会写入 `message_send_outbox`，由 HTTP upstream delivery 服务派发到上游。

### HTTP 上游派发配置

默认未配置真实上游时，系统使用本地 sandbox provider，返回确定性的 `SANDBOX-{messageId}`，方便本机验证。
如需接入 HTTP 上游，在配置中启用：

```yaml
ycsopen:
  sms:
    upstream-http:
      enabled: true
      base-url: https://provider.example.com
      path: /messages
      timeout-ms: 1000
```

派发请求会带 `Idempotency-Key` 请求头。上游响应支持：

```json
{"providerMessageId":"UP-123","status":"ACCEPTED"}
```

若上游明确拒绝，返回：

```json
{"status":"REJECTED","errorCode":"BLACKLIST","errorMessage":"blocked"}
```

未知结果不会自动重试，outbox 会保持 claimed 并记录错误，避免可能已被上游接收的消息被重复发送。

### 状态查询与回执

状态查询：`GET /api/v1/sms/status/{messageId}`，使用同一套 HMAC 鉴权，只允许查询本机构消息。
响应包含提交流水、发送状态、上游消息 ID、outbox 状态、计费状态和错误信息，不返回手机号明文。

回执入口：`POST /api/v1/sms/receipts`

```json
{
  "messageId": "MSG_1700000000000_ABCDEF12",
  "providerMessageId": "UP-123",
  "channelId": 42,
  "providerStatus": "DELIVERED",
  "safePayload": "{\"status\":\"DELIVERED\"}"
}
```

`DELIVERED`/`SUCCESS` 会将消息置为 `DELIVERED` 并确认计费；`FAILED`/`REJECTED` 会将消息置为
`FAILED` 并冲正计费。重复回执只写入一次报告，不重复确认或冲正。

## 初始化数据库

### 本机 root 可免密登录

仓库脚本会创建数据库、无广域授权的应用账号和独立 Flyway 迁移账号。表结构由应用启动时的
Flyway 自动创建；迁移完成后的 callback 再按表授予应用运行权限：

```bash
cd core
./tools/init-db.sh
```

脚本默认值：

| 项目 | 默认值 |
|---|---|
| 数据库 | `ycsopen_sms` |
| 数据库用户 | `ycsopen` |
| 数据库密码 | `ycsopen` |
| Flyway 用户 | `ycsopen_migrator` |
| Flyway 密码 | `ycsopen_migrator` |
| 字符集/排序规则 | `utf8mb4` / `utf8mb4_unicode_ci` |

也可以传入自定义值：

```bash
./tools/init-db.sh <database> <app-user> <app-password> <migration-user> <migration-password>
```

本地 helper 的数据库名/用户名只接受字母、数字、下划线，密码只接受字母、数字及
`_.@%+=!-`，避免把参数解释为 SQL。需要其他密码字符时，请使用参数化的基础设施管理工具创建账号。

### root 需要密码或 MySQL 在容器中

先用有建库/授权权限的账号进入 MySQL：

```bash
mysql -h 127.0.0.1 -P 3306 -u root -p
```

执行：

```sql
CREATE DATABASE IF NOT EXISTS ycsopen_sms
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;

CREATE USER IF NOT EXISTS 'ycsopen'@'%' IDENTIFIED BY 'ycsopen';
CREATE USER IF NOT EXISTS 'ycsopen_migrator'@'%' IDENTIFIED BY 'ycsopen_migrator';
REVOKE ALL PRIVILEGES ON ycsopen_sms.* FROM 'ycsopen'@'%';
GRANT ALL PRIVILEGES ON ycsopen_sms.* TO 'ycsopen_migrator'@'%' WITH GRANT OPTION;
FLUSH PRIVILEGES;
```

首次创建且应用账号没有任何 schema grant 时，`REVOKE` 可能提示没有可撤销的授权，可忽略该条。
运行账号不得拥有全局授权；迁移 callback 会先移除该 schema 的广域授权，避免其通过 `TRUNCATE`、
`DROP` 或拆除触发器绕过审计保护，然后对普通业务表逐表授予 DML，对
`privileged_operation_audits`、`security_events` 仅授予 `SELECT/INSERT`，并只授予执行审计终态
存储过程所需的 `EXECUTE`。

上述两组默认凭据仅用于源码开发。对外部署时必须全部替换，并同步设置 `DB_USERNAME`、
`DB_PASSWORD`、`DB_MIGRATION_USERNAME`、`DB_MIGRATION_PASSWORD`；`DB_USER_HOST` 必须与创建账号时
的 host 部分一致。

## 配置后端

### 生成开发 JWT 密钥

启动后端前应替换不安全的 JWT 默认值：

```bash
export JWT_SECRET="$(openssl rand -base64 48 | tr -d '\n')"
```

- `JWT_SECRET` 用于签发控制台 JWT。
- 不要把真实密钥写入 Git、README、启动脚本或 systemd unit；使用权限受控的环境文件。

### 默认关闭模式

`YCSOPEN_CRYPTO_STORAGE_ENABLED` 和 `YCSOPEN_OBJECT_STORE_ENABLED` 默认均为 `false`。服务可以在该模式
启动，用于登录、页面和不接触受保护数据的有限开发，但它不是完整业务模式：

- 短信提交需要保护手机号时失败关闭；
- 机构注册材料的上传、读取和 claim 操作不可用；
- 不会退回明文存储，也不存在单一环境变量字段密钥的兼容路径。

### 启用生产加密存储

受保护流程使用 PKCS#11，不读取单个应用字段密钥。启用前必须同时满足下面四组依赖；任一项缺失或
身份不一致都会导致启动或受保护操作失败关闭。

#### 1. PKCS#11 模块和凭据

```ini
YCSOPEN_CRYPTO_STORAGE_ENABLED=true
YCSOPEN_CRYPTO_STORAGE_ADAPTER=SUN_PKCS11
YCSOPEN_PKCS11_MODULE_PATH=/opt/vendor/pkcs11/libvendor-pkcs11.so
YCSOPEN_PKCS11_ALLOWED_MODULE_PATHS=/opt/vendor/pkcs11/libvendor-pkcs11.so
YCSOPEN_PKCS11_SLOT_ID=<non-negative-slot-id>
YCSOPEN_PKCS11_TOKEN_IDENTITY=<exact-token-label>
YCSOPEN_PKCS11_CREDENTIAL_REFERENCE=YCSOPEN_PKCS11_PIN
YCSOPEN_PKCS11_PIN=<token-user-pin>
```

`YCSOPEN_PKCS11_MODULE_PATH` 必须是 canonical 普通文件路径，并且精确出现在逗号分隔的
`YCSOPEN_PKCS11_ALLOWED_MODULE_PATHS` 中；不能使用符号链接。slot、token identity 和 PIN 必须对应
同一设备。`YCSOPEN_PKCS11_CREDENTIAL_REFERENCE` 保存的是环境变量名，默认是
`YCSOPEN_PKCS11_PIN`，配置文件本身不得保存 PIN。

模块必须提供 `CKM_AES_GCM`、`CKM_SHA256_HMAC`，密钥必须具有
`CKA_TOKEN`、`CKA_PRIVATE`、`CKA_SENSITIVE`、`CKA_NOT_EXTRACTABLE` 属性。

#### 2. 五种用途分离的密钥

| 用途 | 算法 | PKCS#11 label/alias | 数据库 `provider_key_reference` |
|---|---|---|---|
| `FIELD_ENCRYPTION_KEK` | AES-256 | `ycs.field-encryption-kek.v1` | `field-kek.v1` |
| `SNAPSHOT_RECOVERY` | AES-256 | `ycs.snapshot-recovery.v1` | `snapshot-recovery.v1` |
| `MOBILE_BLIND_INDEX` | HMAC-SHA-256 | `ycs.mobile-blind-index.v1` | `mobile-index.v1` |
| `OBJECT_CAPABILITY_DIGEST` | HMAC-SHA-256 | `ycs.object-capability-digest.v1` | `object-digest.v1` |
| `REGISTRATION_UPLOAD_DIGEST` | HMAC-SHA-256 | `ycs.registration-upload-digest.v1` | `registration-digest.v1` |

所有五把密钥都必须在同一已配置 token 中存在、不可导出且用途不能混用。由 HSM 管理员创建密钥后，
再以数据库管理员身份执行一次非秘密引用初始化：

```sql
INSERT INTO ycs_crypto_key_references
  (purpose, key_version, provider_id, provider_key_reference, key_state,
   wrap_operation_count, rotation_required, optimistic_version)
VALUES
  ('FIELD_ENCRYPTION_KEK', 1, 'pkcs11', 'field-kek.v1', 'ACTIVE', 0, FALSE, 0),
  ('SNAPSHOT_RECOVERY', 1, 'pkcs11', 'snapshot-recovery.v1', 'ACTIVE', 0, FALSE, 0),
  ('MOBILE_BLIND_INDEX', 1, 'pkcs11', 'mobile-index.v1', 'ACTIVE', 0, FALSE, 0),
  ('OBJECT_CAPABILITY_DIGEST', 1, 'pkcs11', 'object-digest.v1', 'ACTIVE', 0, FALSE, 0),
  ('REGISTRATION_UPLOAD_DIGEST', 1, 'pkcs11', 'registration-digest.v1', 'ACTIVE', 0, FALSE, 0);
```

这段 SQL 只能登记引用，不能创建、导入或验证 HSM 密钥。仓库当前没有可执行的生产密钥 bootstrap
命令，也没有完成 HSM 厂商间通用的创建/轮换流程；运维人员必须用厂商受支持的管理工具创建上述
密钥并核对属性，不能把测试中的 SoftHSM provisioner 当作生产工具。因此，在完成厂商侧步骤和一次
真实环境预检之前，不能宣称受保护生产流程已经就绪。

#### 3. 加密快照目录

```ini
YCSOPEN_ENCRYPTED_SNAPSHOT_STORE_ROOT=/var/lib/ycsopen-sms/encrypted-snapshots
```

该目录必须预先创建，使用私有权限，不得是符号链接。密钥生命周期检查和 `phase03-migration`
快照命令必须指向同一 canonical 根目录；命令额外需要的签名配置见
[Phase 3 加密迁移与快照命令](#phase-3-加密迁移与快照命令)。

#### 4. 私有对象存储

```ini
YCSOPEN_OBJECT_STORE_ENABLED=true
YCSOPEN_OBJECT_STORE_BUCKET=<private-bucket>
YCSOPEN_OBJECT_STORE_REGION=<region>
YCSOPEN_OBJECT_STORE_ENDPOINT=https://s3.internal.example
YCSOPEN_OBJECT_STORE_ALLOWED_ENDPOINTS=https://s3.internal.example
YCSOPEN_OBJECT_STORE_CREDENTIAL_PROVIDER=DEFAULT_CHAIN
YCSOPEN_OBJECT_STORE_PATH_STYLE_ACCESS=false
```

bucket 必须是私有 bucket。显式 endpoint 必须精确出现在 allowlist 中，生产环境应使用 HTTPS；凭据由
AWS SDK 默认链、容器角色或实例角色提供，不写入应用配置。对象存储只能在加密存储同时启用时启动。

## 初始化本地管理员账号

Flyway 在首次以 `dev` profile 启动时会执行 `R__create_default_admin.sql`，自动创建 Web
控制台管理员。如果数据库中已有 `admin` 账号，迁移会保留原有密码和状态。

初始化后的开发登录凭据：

| 项目 | 值 |
|---|---|
| 登录地址 | `http://localhost:5173/login` |
| 用户名 | `admin` |
| 密码 | `Admin@123456` |
| 角色 | `ADMIN` |

默认密码只用于本地开发。非 `dev` profile 不会加载该迁移，对外部署应通过受控流程创建独立账号。

账号连续输错密码达到 5 次会被锁定。当前没有管理员解锁页面，可在本地数据库中执行：

UPDATE users

## 部署前端与 Nginx

复制静态产物：

```bash
sudo install -d /var/www/ycsopen-sms
sudo cp -R web/dist/. /var/www/ycsopen-sms/
```

创建 Nginx server 配置：

```nginx
server {
    listen 80;
    server_name sms.example.com;

    root /var/www/ycsopen-sms;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        # 仅支持同机单层 Nginx：覆盖客户端传入的 XFF，禁止使用
        # $proxy_add_x_forwarded_for，否则攻击者可伪造审计归因地址。
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

后端只在直接连接来自本机回环地址时接受只含一个数值 IP 的 `X-Forwarded-For`；非回环直连携带的
转发头以及包含逗号的代理链都会被忽略。当前支持的部署拓扑是同机单层 Nginx，配置必须覆盖而不是追加该请求头。
因而该示例要求 Nginx 与后端同机，并禁止外部直接访问 8080。若改为跨主机反向
代理，需先实现并验证新的显式可信代理 allowlist，不能直接信任客户端提供的转发头。

`try_files ... /index.html` 是 React Router 刷新子路径时不返回 404 的关键。验证配置并重载：

```bash
sudo nginx -t
sudo systemctl reload nginx
```

正式环境应在 Nginx 配置 TLS 证书，只开放 80/443，并让 MySQL、Redis、8080 仅在受控网络可达。

### 系统配置管理

平台管理员从“系统配置”菜单进入 `/admin/system/configuration`。该页面当前只允许修改服务端封闭
注册表中的三项配置，不接受任意键：

| 配置键 | 类型与约束 | 默认值 | 运行时作用 |
|---|---|---|---|
| `security.login.max-failures` | `3` 到 `20` 的整数 | `5` | 登录连续失败锁定阈值 |
| `security.login.unusual-ip-enabled` | `true` / `false` | `true` | 是否检测登录来源 IP 变化 |
| `security.export.signing-key-ref` | `env:UPPER_SNAKE_CASE` 引用 | `env:YCS_SMS_EXPORT_SIGNING_KEY` | 导出签名密钥的环境变量引用；页面只显示 `env:••••••` |

操作顺序为：编辑字段 → 填写变更原因 → 保存草稿 → 检查草稿与变更键 → 确认激活。保存草稿不会
改变运行时；激活成功后数据库版本、当前版本指针和内存运行时状态才切换。历史版本不可修改，
“回滚”会以选中的历史快照创建并激活一个新版本。并发管理员基于旧版本提交时会收到冲突提示，
必须刷新后重新确认。运行时预检拒绝时，原生效版本保持不变，历史中只记录安全错误码。
页面显示最新 50 条不可变版本记录；它用于近期运维与回滚，不是完整历史报表。操作失败会保留尚未
提交的本地编辑并显示安全提示，前端依据响应的 `data.errorCode` 区分并发冲突与热加载拒绝。

权限分为 `system:configuration:menu`、`system:configuration:read`、
`system:configuration:write` 和 `system:configuration:activate`；平台 `ADMIN` 有显式覆盖。菜单同时
要求 menu 和 read；直接访问页面仍由服务端 read 权限控制。只有 read 的账号仅可查看；具有 write
但没有 activate 的账号可保存草稿但不能激活或回滚。密钥值本身不得输入该页面，只能登记环境变量
名称；引用指向的秘密必须由部署环境的秘密管理系统注入。配置版本表由数据库触发器限制为明确的
生命周期转换并禁止删除，运行账号不能改写快照、校验和或操作人。
新增登记键会以其代码默认值补入旧版本快照；未知旧键仍拒绝加载。删除或重命名登记键前必须先提供
显式兼容迁移，不能直接修改注册表。

### 上传机构注册证明材料

注册证明材料使用私有暂存会话，不使用外部 URL。固定顺序如下：

1. `POST /api/v1/console/tenants/registration-object-sessions` 创建会话。保存响应中的
   `registrationObjectSessionId`、一次返回的 `regup_v1_` 凭据和 `expiresAt`；不要记录或持久化
   完整凭据。
2. 对每个用途调用
   `POST /api/v1/console/tenants/registration-object-sessions/{sessionId}/objects/{purpose}`。
   请求头必须是 `X-Registration-Upload-Token`，正文必须是 `multipart/form-data`，且只能包含一个
   名为 `file` 的文件 part。
3. 注册 JSON 只提交 `registrationObjectSessionId` 与对象 ID 字段
   `businessLicenseObjectId`、`legalRepIdFrontObjectId`、`legalRepIdBackObjectId`、
   `shortlinkDomainProofObjectId`、`trademarkProofObjectId`。
4. 不再继续注册时，用
   `DELETE /api/v1/console/tenants/registration-object-sessions/{sessionId}` 显式关闭会话，并携带
   同一个 `X-Registration-Upload-Token`。

用途与限制必须严格匹配：

| `{purpose}` | 必填性 | 允许媒体 | 最大明文字节 | 最大完整 YCSE/v1 信封字节 |
|---|---|---|---:|---:|
| `business-license` | 必填 | PDF/JPEG/PNG | 10,485,760 | 10,485,905 |
| `legal-rep-id-front` | 必填 | JPEG/PNG | 5,242,880 | 5,243,025 |
| `legal-rep-id-back` | 必填 | JPEG/PNG | 5,242,880 | 5,243,025 |
| `shortlink-domain-proof` | 可选 | PDF/JPEG/PNG | 10,485,760 | 10,485,905 |
| `trademark-proof` | 可选 | PDF/JPEG/PNG | 10,485,760 | 10,485,905 |

服务端同时校验声明媒体、实际签名字节、明文上限和完整信封上限。会话 TTL 固定为 `PT24H`，状态为
`OPEN -> CLAIMED | CLOSED | EXPIRED`。同一会话凭据可以在 `OPEN` 内顺序上传全部五种用途，也可以
替换同一用途当前的 `STAGED` 对象；它不能跨 session 或 tenant-draft。claim、close、expiry 后均不能
继续使用。

每个 purpose 最多预留 3 次 admitted attempt，每个 session 最多 15 次。预留发生在媒体、大小和
签名检查之后、加密和私有存储之前；并发请求不会超过任一上限。预留后的 provider、store、元数据或
reconciliation 失败会烧掉 slot。达到上限固定返回 HTTP 429
`REGISTRATION_UPLOAD_LIMIT_REACHED`。

`regup_v1_` 由非秘密 lookup ID 和 32 字节随机 secret 构成。服务端只保存 `REGISTRATION_UPLOAD`
用途、tenant-draft/session 绑定的版本化摘要；新签发只用 ACTIVE，验证接受存储的 ACTIVE/RETIRING
版本并使用常量时间比较。未知、RETIRED、REVOKED 或 `OBJECT_CAPABILITY` 跨域凭据失败关闭。

旧 `*Url` 字段和任何 HTTP(S) 形态的值不再兼容，固定返回 HTTP 422
`LEGACY_OBJECT_URL_NOT_ACCEPTED`；缺少必填对象返回 `REGISTRATION_OBJECT_REQUIRED`。上传接口的
稳定错误为 `REGISTRATION_UPLOAD_INPUT_INVALID`、`REGISTRATION_UPLOAD_TOKEN_INVALID`、
`REGISTRATION_UPLOAD_SESSION_NOT_OPEN`、`REGISTRATION_UPLOAD_SESSION_EXPIRED`、
`REGISTRATION_UPLOAD_MEDIA_TYPE_NOT_ACCEPTED`、`REGISTRATION_UPLOAD_SIZE_LIMIT_EXCEEDED`、
`REGISTRATION_UPLOAD_SIGNATURE_MISMATCH`、`REGISTRATION_UPLOAD_LIMIT_REACHED`、
`REGISTRATION_UPLOAD_UNAVAILABLE`。响应只返回 `pobj_v1_*`、purpose 和 expiry；不会返回或接收
bucket、key、public reference、presigned reference，也不会泄漏完整 token、存储定位或 provider 细节。

## Phase 3 加密迁移与快照命令

`phase03-migration` 是显式运维命令，不会随应用启动自动执行。除 `--help` 外，命令启动前必须同时提供：

- `YCSOPEN_PHASE03_MIGRATION_CONFIG`：字节级 canonical JSON 配置的绝对路径；
- `YCSOPEN_PHASE03_MIGRATION_CONFIG_SIGNATURE`：配置的 canonical Base64 Ed25519 detached signature 文件；
- `YCSOPEN_PHASE03_MIGRATION_CONFIG_PUBLIC_KEY`：由进程启动环境独立固定的 Ed25519 X.509 DER 公钥 Base64，不能从配置文件自举；
- `YCSOPEN_ENCRYPTED_SNAPSHOT_STORE_ROOT`：已有、非符号链接的私有目录；必须与签名配置中的 `snapshot.storeRoot` 解析成同一个 canonical 路径。

签名配置只保存凭据环境变量名，不保存密码或 PIN。其 `snapshot.mysqldumpPath`、
`snapshot.mysqlPath` 必须是 raw canonical、全路径无符号链接的本机可执行文件；
`snapshot.mysqldumpSha256`、`snapshot.mysqlSha256` 必须分别填写对应文件的
`sha256:<64位小写十六进制>`。可执行文件只能位于代码固定的 `/usr/bin` 或
`/opt/ycsopen/mysql-client` 受信根下，不接受 Homebrew、`/usr/local`、临时目录、snapshot/config/data
目录或另一个可配置根。服务必须以非 root 身份运行：effective UID 和 real UID 分别通过 root-owned 固定工具
`/usr/bin/id -u` 与 `/usr/bin/id -ru` 获取；任一 UID 为 `0` 或两者不相等都拒绝。两个 probe 只接受有界、单行、无前导零的
十进制结果；超时、输出超限、stderr、非零退出或格式异常均失败关闭。在组合时和每次读取
`Database.password()` 之前，
进程都会对 leaf 与全部 ancestor 执行 `NOFOLLOW_LINKS`、raw-canonical、root uid/gid、非 group/other 可写、
无 ACL、leaf regular/executable、有界长度、inode 和签名 SHA-256 检查。ACL 不依赖可选的 Java attribute view：
macOS 固定执行 `/bin/ls -lde -- <path>` 并拒绝权限 `+`/任何 ACL entry，Linux 固定执行
`/usr/bin/ls -ldn -- <path>` 并拒绝 `+`；未知 OS、未知输出、超时、超限、stderr 或非零退出全部失败关闭。
`id`/`ls` helper 启动时也清空继承环境，仅保留 `LC_ALL=C`、`LANG=C`且不接触凭据。执行文件 authority
验证在 HSM session 打开前完成。`ProcessBuilder` 启动 MySQL 客户端前清空继承环境，只注入
`MYSQL_PWD`、`LC_ALL=C`、`LANG=C`、`TZ=UTC`，不继承 `PATH/HOME/TMPDIR/LD*/DYLD*/MYSQL_HOME/LIBMYSQL_PLUGIN_DIR`。
配置签名覆盖：

```text
ASCII("YCS-PHASE03-PRODUCTION-CONFIG-SIGNATURE/v1\0")
|| u32be(canonical_config_byte_length)
|| exact_canonical_config_bytes
```

非 canonical JSON、坏签名、错误公钥、缺少任一启动输入、可写的不可信路径、符号链接或根目录不一致都会在连接
MySQL/HSM 前失败。私钥必须保留在离线发布系统，不得放入仓库或部署主机配置。

该执行边界信任 root 管理员和不可变部署镜像对上述两个受信根的管理。威胁模型允许攻击者写 snapshot、config
或 data 目录，但攻击者不能提权、ptrace 服务进程、mount 覆盖受信根或获得 root；root/部署镜像已被攻破不在该边界内。

签名配置中的 JDBC 账号是快照操作账号：必须能够读取源 schema，并能够在运维人员预先创建的目标空 schema
中建表和写入数据。命令不会替账号扩权，也不会自动创建或清空目标 schema；仅有源库权限的普通应用账号不能用于
`snapshot-restore`。恢复目标必须是本次恢复专用且独占的 schema，从 fresh-schema 检查开始到完成后的校验结束不得有
其他写入者。建议为该账号设置短期凭据，并在恢复完成后立即撤销目标库写权限。

快照操作的固定命令为：

```bash
phase03-migration snapshot-create \
  --snapshot-id <id> --environment <id> \
  --database-instance-fingerprint <64-hex> --schema <source-schema> \
  --flyway-set-digest <64-hex> --global-sequence <nonnegative-decimal> \
  --signer-key-version <version>

phase03-migration snapshot-restore \
  --snapshot-id <id> --pair-digest <64-hex> --target-schema <fresh-schema>

phase03-migration snapshot-delete \
  --snapshot-id <id> --snapshot-digest <64-hex>
```

`snapshot-create` 只使用数据库中唯一可写的 `SNAPSHOT_RECOVERY` 密钥引用，并通过固定 argv 的
`mysqldump` 直接流入加密分块，不产生明文 dump 文件。创建后需离线签署 writer/snapshot manifest pair，再执行
`preflight`；生产 preflight 会在数据库 CAS 之前，从同一个 FileStore 验证精确 manifest、全部分块摘要和逐块解密
认证。`snapshot-restore` 只从该 FileStore 取 manifest，并要求数据库当前 accepted pair 精确匹配；目标 schema
必须事先创建、不同于源 schema 且没有任何表。`snapshot-delete` 不依赖会被后续 admission 替换的 current pair，
但必须提供 retained canonical manifest 的精确 SHA-256 digest。全局序列从 `0` 开始合法，创建、签名 pair、数据库
admission 和恢复使用同一个非负整数契约。

创建快照和校验恢复目标使用同一套确定性 dump profile：`--no-defaults`、`--skip-opt`，随后显式启用
`--create-options --set-charset --quote-names --triggers --complete-insert --order-by-primary --hex-blob`，并禁用
add-drop-table、locks、disable-keys、extended-insert、comments 和 dump-date；字符集固定为 `utf8mb4`，时区为 UTC，
进程环境固定 `LC_ALL=C`、`TZ=UTC`。源与恢复目标的所有基础表必须使用 InnoDB；业务表必须存在稳定的非空唯一顺序，
routine/event 数量必须为零。view 不作为基础表导出，trigger 按上述 profile 导出。

恢复完成标记只是快速提示，不是当前数据库正确性的证据。首次恢复在写标记之前、重复恢复在返回
`already_complete` 之前，都会重新认证 retained manifest/全部加密分块，并将解密 SQL 的有界流式
`(byte length, SHA-256)` 与目标 schema 使用同一 profile 实时重导出的结果比较；目标被删除、被改写或 retained chunk
缺失/损坏时都返回 `25`，且不会写入或信任完成标记。完成标记按 snapshot ID 独立目录存放，删除 `a` 不会删除
`a.b` 的恢复状态；两个 target 并发首次发布同一 snapshot 的完成标记时，独立目录创建也使用精确的
create-or-revalidate 合约，不会将合法的同时创建误判为恢复失败。

命令只输出无敏感信息的单行 JSON。快照缺失、分块不完整、摘要/认证失败、非 fresh schema 等固定使用退出码
`25`；key/provider 不可用使用 `26`。完整选项与退出码以
`core/src/main/resources/security/migration/phase03-migration-cli-contract.json` 和 `--help` 为准。

## 停止服务

开发模式在对应终端按 `Ctrl+C`。systemd 部署使用：

```bash
sudo systemctl stop ycsopen-sms-core
```

容器依赖使用：

```bash
docker stop ycsopen-mysql ycsopen-redis
```

## 升级

升级前先备份数据库和部署环境的密钥/配置。不要把密钥备份进源码目录。

```bash
mysqldump -h <mysql-host> -u <backup-user> -p \
  --single-transaction ycsopen_sms > ycsopen_sms-backup.sql

git pull --ff-only

cd core
mvn test
mvn clean package

cd ../web
npm ci
npm test
npm run build
```

随后替换 JAR 和 `web/dist/`，重启后端，验证健康检查和登录。应用启动时 Flyway 会执行尚未应用的
migration；若 Flyway validation 失败，不要删除历史记录强行继续，应核对 migration 是否被改写。

## 故障排查

### 加密存储启动时报 `CRYPTO_STORAGE_CONFIGURATION`

不要生成临时字段密钥绕过错误。该错误表示启用模式的 PKCS#11 模块 allowlist、slot、token identity、
PIN 环境引用、固定算法/属性或五种用途引用至少有一项不一致。按
[启用生产加密存储](#启用生产加密存储)逐项核对 HSM 与 `ycs_crypto_key_references`；如果只是有限本地
开发，应明确保持 `YCSOPEN_CRYPTO_STORAGE_ENABLED=false`，受保护业务仍会失败关闭。

### JWT 报 weak key

原因：`JWT_SECRET` 长度不足。

```bash
export JWT_SECRET="$(openssl rand -base64 48 | tr -d '\n')"
```

### MySQL `Access denied`

检查实际主机、端口、账号授权和环境变量：

```bash
mysql -h 127.0.0.1 -u ycsopen -p ycsopen_sms
env | grep -E 'SPRING_DATASOURCE_URL|DB_USERNAME|DB_MIGRATION_USERNAME|DB_USER_HOST'
```

不要把上述 `env` 输出粘贴到公开 issue，它可能包含密码。

### Redis 连接失败

```bash
redis-cli -h "${REDIS_HOST:-localhost}" -p "${REDIS_PORT:-6379}" ping
```

确认返回 `PONG`，并检查防火墙、认证和容器端口映射。

### Web 登录提示用户名或密码错误

- 确认已执行管理员初始化 SQL。
- 确认后端健康检查通过。
- 检查浏览器 Network 中 `/api/v1/console/auth/login` 的响应。
- 连续错误达到 5 次后，按本文 SQL 将账号恢复为 `ACTIVE` 并清零失败次数。

### 前端调用到了错误的后端

开发环境默认代理到 `http://127.0.0.1:8080`。后端使用其他本机端口时，在启动 Vite 前设置
`VITE_BACKEND_TARGET=http://127.0.0.1:<端口>`；为避免误把凭据代理到外部站点，该值只接受 HTTP
loopback 地址。部署环境继续让 Nginx 提供同源 `/api/`。

### 刷新前端子页面返回 404

Nginx 缺少 SPA fallback。确认 `location /` 中有：

```nginx
try_files $uri $uri/ /index.html;
```

### Flyway validation 失败

不要修改已经执行过的 migration。比较数据库 `flyway_schema_history` 与
`core/src/main/resources/db/migration/`，新增一个更高版本 migration 完成修正。

## 安全检查清单

- [ ] 数据库默认密码已替换，MySQL/Redis 未暴露到公网。
- [ ] Flyway 与应用账号已分离，应用账号无全局/schema 级授权，审计表只有 `SELECT/INSERT`。
- [ ] 若 MySQL 开启 binary log，`log_bin_trust_function_creators=ON` 已在执行 V1500 前验证。
- [ ] `JWT_SECRET` 和 PKCS#11 PIN 来自受控秘密管理系统，配置中只保存 PIN 环境变量名。
