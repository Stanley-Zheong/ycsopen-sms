# YCSOPEN-SMS PRD V2 优化草案

> 基于 `docs/PRD.md` v1.3.0、`docs/PRD_REVIEW.md`、`docs/frontend页面实现规范.md`、当前 GitHub issue/PR 记录重新核对。本文不替代原 PRD 的功能清单，而是把 V2 的业务闭环、数据闭环、指令闭环补齐，供后续正式评审和拆分 issue 使用。

## 1. V2 修订目标

V1 PRD 的功能覆盖较全，但实现后期集中出现“页面看不懂、按钮语义不清、孤立输入框、表单布局反复调整、计费/试用/投诉归因后补”等问题，说明 PRD 仍偏“模块清单”和“字段清单”，对跨角色业务闭环、数据归属、指令语义描述不足。

V2 的目标是：

- 把短信平台从“功能模块集合”重构为“销售、运营、财务、技术、客户”五个系统共同驱动的闭环产品。
- 对每条主链路明确业务流、数据流、指令流，避免只有页面或字段、没有动作结果。
- 对每个可操作按钮定义目标对象、前置条件、执行结果、失败反馈、审计记录和自动化验收口径。
- 将 UI/交互验收前置到 PRD，而不是实现后用缺陷单反复修补。
- 保留 V1 的合规、计费、路由、投诉、审计要求，但补齐跨模块源数据、状态机和证据链。

## 2. 五个系统视角

用户提到“四个系统视角”，但实际列出运营、销售、财务、技术、客户五类。V2 按五个系统建模，避免销售和客户、运营和技术职责混淆。

| 系统视角 | 核心目标 | 主数据 | 可发起指令 | 必须看到的结果 |
|---|---|---|---|---|
| 销售系统 | 获客、试用、签约、续约、终止合作 | 线索、机构档案、合同、价格版本、商务经理、客户等级 | 开通试用、转正式签约、变更客户等级、发起终止合作 | 机构生命周期、合同状态、可用额度、续费/终止风险 |
| 运营系统 | 合规审核、通道质量、投诉处置、告警处理 | 签名、模板、通道、路由规则、投诉工单、告警记录 | 审核通过/驳回、暂停/恢复通道、处置投诉、确认/解决/静音告警 | 每个动作影响范围、当前风险、处置证据、是否恢复正常 |
| 财务系统 | 余额、授信、计费、对账、结算、发票 | 账户、充值、扣费流水、账单、结算单、发票、授信额度 | 充值审核、授信调整、生成账单、确认对账、冻结欠费机构 | 余额/授信变化、计费依据、对账差异、财务审计轨迹 |
| 技术系统 | 接入、路由、发送、回执、回调、可观测性 | API Key、CMPP 凭证、消息、任务、回执、上行、Webhook、日志 | 鉴权、限流、路由、重试、回调、归档、告警触发 | traceId、消息最终状态、失败原因、重试结果、运行健康 |
| 客户系统 | 自助接入、发送、查询、对账、资质维护 | 资质、签名、模板、发送记录、回执、上行、余额、发票 | 提交资质、申请签名模板、发送短信、配置回调、导出详单 | 申请状态、发送结果、扣费明细、回调记录、可申诉路径 |

## 3. 业务流优化

### 3.1 机构生命周期闭环

V2 将机构生命周期定义为一条销售、运营、财务、客户共同参与的主线：

```text
注册/线索
→ 资质提交
→ 运营审核
→ 试用开通
→ API/CMPP 接入准备
→ 签名/模板申请与审核
→ 试用发送
→ 转正式签约
→ 充值或授信
→ 正式发送与月度对账
→ 风险/费用/投诉干预
→ 续约、冻结或终止合作
```

V2 优化点：

- 试用不是“机构状态字段”，而是一套有额度、有效范围、价格策略、发送边界、到期处置的商业产品。
- 转正式签约必须同时写入合同、价格版本、计费模式、授信或预付费账户规则。
- 停止合作必须串联运营风险、财务结清、技术凭证吊销、客户历史数据留存。
- 所有生命周期动作必须在机构时间线中可见，供销售、运营、财务、客户共同追溯。

### 3.2 消息发送闭环

V2 将每条短信的闭环定义为：

```text
客户提交
→ API/CMPP 鉴权
→ 幂等检查
→ 签名/模板状态校验
→ 模板变量渲染
→ 最终文本内容审核
→ 黑白名单/第三方风险名单检查
→ 频次/限流检查
→ 试用额度或账户余额/授信预占
→ 路由选通道
→ 发送任务生成
→ 上游受理
→ 回执归一化
→ 计费确认或冲正
→ Webhook 回调
→ 详单/统计/告警更新
```

V2 优化点：

- “最终文本内容审核”写成硬规则，避免只审核模板原文而绕过变量内容。
- 计费必须和试用额度、通道成本价、客户价格版本联动，不能后补。
- 消息状态、计费状态、回调状态分离；一个消息发送失败不等于账务已冲正，也不等于 Webhook 已通知。
- 失败原因使用统一错误码和可解释文案，进入客户详单、运营监控、财务对账三套视图。

### 3.3 合规资源闭环

签名、模板、免审规则、短链、黑白名单属于合规资源。V2 统一其生命周期：

```text
客户申请/平台创建
→ 材料校验
→ 风险评估
→ 运营审核
→ 上游报备
→ 可用范围生效
→ 发送引用
→ 投诉/巡检联动下线
→ 复核恢复或永久停用
```

V2 优化点：

- 每个资源必须有“可用范围”：机构、产品、签名、模板、通道、时间、场景。
- 审核通过不等于所有通道可用；通道报备状态必须进入路由候选判断。
- 免审规则不是绕过合规，而是有范围、有效期、审批记录、命中日志的合规策略。

### 3.4 投诉、告警与处置闭环

V2 将投诉和告警统一为“风险事件”：

```text
事件产生
→ 归因到机构/通道/签名/模板/消息
→ 严重级别判定
→ 处置建议
→ 人工确认或策略自动执行
→ 暂停/恢复/入黑/下线等动作
→ 客户通知
→ 复盘和规则优化
```

V2 优化点：

- 告警历史页面的按钮必须直接表达动作语义，例如“确认告警”“标记解决”“静音规则”，不能只显示无上下文按钮。
- 投诉占比的分子来源、统计刷新频率、人工录入滞后风险必须在页面显式提示。
- 无法归因的投诉不能静默丢弃，应进入“待补充归因”队列，并从看板中单独展示。

### 3.5 财务闭环

V2 将财务闭环定义为：

```text
价格版本
→ 试用/预付费/后付费规则
→ 发送预占或授信占用
→ 回执确认计费
→ 冲正
→ 账单生成
→ 客户确认
→ 结算/开票
→ 欠费预警/冻结/终止
```

V2 优化点：

- 每条计费流水必须记录价格版本和通道成本价快照，不能事后依赖当前价格表反推。
- 预付费余额、后付费授信、试用额度是三类不同额度，页面和接口需明确展示。
- 财务导出与对账单必须有生成快照，后续数据变化不能改变已生成账单。

## 4. 数据流优化

### 4.1 主数据归属

| 数据域 | 归属系统 | 写入者 | 下游使用者 | V2 约束 |
|---|---|---|---|---|
| 机构档案/资质 | 销售、客户、运营 | 客户提交，运营审核 | 销售、财务、技术 | 未认证机构不得进入正式发送；历史资质版本保留 |
| 合同/价格 | 销售、财务 | 销售/财务 | 计费、账单、客户总览 | 价格按版本生效，消息计费保存快照 |
| 签名/模板/短链 | 客户、运营 | 客户申请，运营审核 | 路由、发送、详单 | 审核状态和通道报备状态共同决定可用性 |
| 通道/路由 | 运营、技术 | 运营配置，技术执行 | 发送、投诉、成本核算 | 配置热更新需有版本号和回滚记录 |
| 消息/回执/上行 | 技术 | 系统写入 | 客户、运营、财务 | 全链路 traceId 必须贯穿提交、任务、回执、回调 |
| 计费/账单 | 财务 | 系统计费，财务确认 | 客户、销售、运营 | 账单生成后按快照审计，不被后续流水改写 |
| 投诉/告警 | 运营、技术 | 系统触发，运营登记 | 销售、财务、客户 | 必须归因或进入待归因队列 |
| 审计日志 | 技术 | 系统自动记录 | 管理员、安全审计 | 所有状态变更动作留痕，不允许绕过审计 |

### 4.2 派生数据口径

V2 对所有看板、导出、报表增加“数据口径卡片”：

- 指标定义：例如投诉占比 = 投诉工单数 ÷ 发送量。
- 来源表/服务：例如投诉工单、发送统计聚合表。
- 刷新频率：实时、近实时、批处理或手工登记。
- 口径限制：人工录入滞后、未知归因、部分通道回执延迟等。
- 最近生成时间和数据版本。

### 4.3 数据质量状态

V2 不再用空值假装正常。核心字段统一有数据质量状态：

- `KNOWN`：已确认并可参与业务决策。
- `UNKNOWN`：当前缺失，不能作为正常值使用。
- `PENDING_ENRICHMENT`：等待补充归因或异步回填。
- `CONFLICTED`：多来源数据冲突，需要人工确认。

适用范围包括投诉归因、通道回执、客户资质、账单差异、Webhook 推送结果。

## 5. 指令流优化

### 5.1 指令分类

| 指令类型 | 示例 | 执行边界 |
|---|---|---|
| 查询 | 搜索、筛选、刷新、导出预览 | 不改变业务状态；必须有明确查询按钮或自动联动规则 |
| 申请 | 客户提交资质、签名、模板、短链 | 进入待审核状态；不能直接生效 |
| 审核 | 通过、驳回、要求补充材料 | 必填审核意见；结果回传客户 |
| 配置 | 调整路由、限流、告警、价格 | 必须有版本、生效范围、回滚路径 |
| 处置 | 暂停机构、暂停通道、入黑、下线资源 | 必须显示影响范围和恢复条件 |
| 财务 | 充值审核、授信调整、账单确认、开票 | 必须关联单据和审计日志 |
| 技术执行 | 路由、重试、回调、归档 | 系统自动执行，必须可追踪和可重放关键证据 |
| 修复 | 重推回调、重跑统计、补充归因 | 不得绕过原始事实，必须保留修复前后差异 |

### 5.2 所有动作按钮的 PRD 契约

每个可点击动作在 PRD 中必须具备以下字段：

| 字段 | 说明 |
|---|---|
| 动作名称 | 使用动词加对象，例如“暂停通道”“确认告警”“重推回执” |
| 目标对象 | 单条记录、批量记录、当前查询结果或配置版本 |
| 触发角色 | 管理员、运营、财务、客户管理员、客户开发者等 |
| 前置条件 | 状态、权限、数据完整性、并发锁、额度边界 |
| 必填输入 | 原因、备注、金额、时间范围、审批意见等 |
| 执行结果 | 状态如何变化、影响哪些下游链路 |
| 失败反馈 | 字段错误、业务拒绝、系统错误、重试方式 |
| 审计记录 | 操作人、时间、IP、目标、参数摘要、结果、traceId |
| 自动化验收 | 可由 Playwright/API 测试观察到的页面或接口变化 |

### 5.3 禁止的指令形态

- 禁止出现只有输入框、没有查询/提交/联动行为的控件。
- 禁止出现脱离目标对象的常驻“原因”输入框。
- 禁止出现只写“操作”“处理”“更多”但不说明结果的按钮。
- 禁止批量动作使用截断展示值作为接口真实参数。
- 禁止静默失败；失败必须在当前动作上下文显示。

## 6. V2 页面与交互要求

V2 将 `docs/frontend页面实现规范.md` 提升为 PRD 验收的一部分：

- 每个业务页面必须说明用户来到此页要完成什么工作，不只是列字段。
- 查询区统一使用 `QueryPanel`，有搜索、重置、必要时展开/收起。
- 表单字段最多四列，label 与控件同一行，控件高度统一。
- 表格空数据也渲染表头和空状态，避免用户误以为页面坏了。
- 行级动作必须在当前行展示；状态管理不能只提供页面级批量入口。
- 新建/编辑统一弹窗或抽屉，包含校验、取消确认、成功刷新、失败重试。
- 所有关键控件提供稳定 `data-testid`，并与 PRD 动作契约一一对应。

- Open item: 将所有 Admin/Tenant 页面补齐“页面目标、主对象、主动作、空状态、错误状态、审计要求”。

- Open item: 明确无法归因投诉的统计口径：是否进入平台总投诉、是否进入机构/通道投诉占比、如何补充归因。
- Open item: 明确平台系统消息的审核豁免、模板维护、供应商失败降级和递归告警保护策略。
- Open item: 明确 1000 TPS 与 10 万条/日的业务口径：容量基线、压测目标、单机构默认配额分别是什么。
- Open item: 将价格版本、通道成本、计费快照写入计费与对账 PRD 字段。
- Open item: 把 Docker 测试环境账号、初始化数据、构建 commit、迁移状态纳入发布验收说明。

## 8. V2 验收原则

- 任何“完成”声明必须有可执行证据：单元测试、集成测试、Playwright、Docker 发布验证或可审计日志。
- 页面验收不只检查是否渲染，还要检查用户是否知道按钮做什么、点击后什么数据变化。
- 数据验收不只检查表存在，还要检查来源、口径、刷新、异常和历史快照。
- 指令验收不只检查接口返回成功，还要检查权限、前置条件、审计、失败反馈和幂等。
- 产品验收以剩余 TODO 是否清空为准，不用模糊进度描述替代明确缺口。
