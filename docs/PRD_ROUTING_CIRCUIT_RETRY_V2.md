# 路由、熔断与重试策略 PRD V2

> 版本：V2 草案  
> 日期：2026-09-21  
> 范围：平台管理端“路由、熔断与重试策略”能力的信息架构、业务流、数据流、指令流、对象生命周期和验收口径；同时补充首页驾驶舱和测试流量模拟器的产品要求。本文只定义产品要求，不包含代码实现。
> 关系：本文是 `docs/PRD_V2.md` 中“消息发送闭环、运营系统、技术系统、动作契约、首页总览”的专题细化；实现时若出现冲突，以本文对路由、熔断、重试和模拟器的生命周期定义为准，并同步回写总 PRD。

## 1. 背景与问题定义

当前页面把“导入规则、模拟路由、熔断状态、重试规则”并列展示，但用户无法理解这些模块之间的业务关系：

- 不知道规则是什么、规则从哪里来、规则一共有几条、CSV 是否就是规则本身。
- 不知道版本的意义、版本何时生效、何时失效、旧版本如何处理、生命周期如何。
- 不知道模拟路由用于什么场景、输入来自哪里、输出会影响什么、是否参与真实发送。
- 不知道熔断状态由谁触发、何时触发、对发送结果有什么影响、如何恢复。
- 不知道重试策略在消息生命周期的哪个阶段生效，和回执、失败码、计费、任务状态之间是什么关系。
- 不知道页面上的操作按钮会产生什么业务结果、写入哪些数据、下游谁会使用。

这是产品信息架构失败，不是单纯 UI 文案问题。V2 必须把页面从“功能控件集合”改为“发送治理工作台”，让运营、技术、客服、财务和客户成功能看懂：谁在什么时候使用它、为什么使用它、用了之后数据和指令如何流转。

## 2. 产品定位

“路由、熔断与重试策略”是短信发送治理链路中的平台侧控制能力，用于决定一条合规短信在进入发送阶段后：

```text
应该走哪个通道或通道池
→ 当前目标通道是否可用
→ 失败后是否重试、何时重试、最多重试几次
→ 决策过程如何留痕、回放、审计
```

页面不是单纯配置页，而是一个“策略发布、策略演练、运行状态、失败动作”的治理工作台。

## 3. 当前实现边界与目标边界

### 3.1 当前事实

当前系统存在两个容易混淆的对象：

| 对象 | 当前用途 | 当前数据源 | 风险 |
|---|---|---|---|
| 真实发送路由规则 | 真实消息提交时选择通道 | `route_rules` | 页面没有解释它与版本化策略的关系 |
| 版本化路由策略 | 控制台导入、模拟、熔断和重试演练 | `routing_policy_versions`、`routing_policy_rules` | 用户会误以为导入后一定参与真实发送 |

V2 PRD 要求页面必须如实说明当前边界：如果版本化策略尚未接入真实发送链路，页面必须明确标识为“策略演练/治理配置，尚未完全接入真实发送”；如果要作为正式生产能力，则后端必须统一真实发送链路与版本化策略链路。

### 3.2 V2 目标边界

V2 的目标状态是统一链路：

```text
客户/API/CMPP 提交短信
→ 鉴权、幂等、签名模板校验
→ 内容安全、黑名单、频控
→ 号码归属与运营商识别
→ 读取当前 ACTIVE 路由策略版本
→ 按规则优先级匹配候选目标
→ 按熔断状态过滤不可用目标
→ 生成发送任务并写入路由决策快照
→ 上游回执归一化
→ 按重试策略决定重试、终止、人工复核或成功结束
→ 计费、详单、回调、统计和审计联动
```

### 3.3 V2 架构决策

为避免继续形成“页面一套、真实发送一套”的产品割裂，V2 明确采用以下决策：

| 决策 | 结论 | 原因 |
|---|---|---|
| 路由规则源 | 版本化路由策略成为真实发送链路的唯一策略源 | 页面发布的规则必须真正影响后续新消息，否则页面只能叫演练台 |
| 旧 `route_rules` | 迁移为历史兼容数据源，只读展示或一次性迁入版本化策略 | 避免同一业务有两套有效规则 |
| 版本作用域 | 支持全局版本和机构版本；机构版本优先，未命中后回落全局版本 | 兼顾平台默认策略和重点客户定制 |
| 回滚机制 | 回滚不直接重启旧版本，而是复制目标历史版本生成新的 `ACTIVE` 回滚版本 | 保持版本号唯一、审计连续、历史不可改写 |
| 重试策略源 | 以“归一化错误类别”为策略源，原始错误码先映射为类别 | 不同上游错误码口径不一致，需先标准化 |
| 运行快照 | 正式发送、重试计划、模拟结果都保存决策快照 | 确保规则失效后仍可审计历史决策 |

旧 `route_rules` 在迁移完成前不得继续作为真实发送的独立决策源。若某阶段暂时仍需读取旧表，页面必须标识“兼容读取中”，且每条真实发送决策快照必须说明使用的是旧规则还是版本化策略。

## 4. 用户与使用场景

| 用户角色 | 使用目的 | 典型场景 | 需要看懂的问题 |
|---|---|---|---|
| 运营 | 调整通道路由、处理异常通道、降低投诉和失败率 | 某运营商发送失败上升，需要切换通道 | 哪些规则会命中、哪些通道会被绕开、什么时候生效 |
| 技术运维 | 验证策略、排查发送失败、确认熔断与重试行为 | 客户反馈短信失败，需定位路由和重试链路 | 一条消息为什么选这个通道，失败后是否重试 |
| 客户成功/销售 | 向客户解释发送失败、延期或通道切换原因 | 重点客户问为什么某批次走备用通道 | 是否平台主动切换、是否影响客户账单和 SLA |
| 财务 | 理解通道切换对成本和计费的影响 | 某通道成本异常，运营调整路由 | 发送通道变化是否影响价格快照和对账 |
| 客户管理员 | 间接感知结果，不直接维护平台路由 | 查看详单、回执、失败原因 | 为什么失败、是否会自动重试、预计何时有最终结果 |

## 5. 核心对象模型

### 5.1 对象关系

```text
路由策略版本 1 ──包含── N 条路由规则
路由规则 N ──指向── 通道 / 通道池 / 默认目标
通道 1 ──拥有── 1 个当前熔断状态
上游回执 / 内部错误 ──归一化为── 错误类别
错误类别 1 ──匹配── 1 条重试策略
一次发送请求 ──产生── 1 条路由决策快照
```

### 5.1.1 对象容量与唯一性

产品必须明确对象可以存在多少条、如何唯一、如何失效。V2 采用以下容量模型：

| 对象 | 作用域 | 唯一性 | 同时有效数量 | 历史保留 | 谁创建 |
|---|---|---|---|---|---|
| 路由策略版本 | 平台全局或指定机构 | `version_no` 全局唯一 | 每个作用域最多 1 个 `ACTIVE` | 永久保留，归档后只读 | 运营或技术 |
| 路由规则 | 所属版本内 | `version_id + priority` 必须唯一；`version_id + condition_type + condition_value` 不得重复 | 每个 `ACTIVE` 版本最多 200 条，超过需分页和冲突检查 | 随版本保留 | 运营导入或编辑 |
| 熔断状态 | 通道维度 | `channel_code` 唯一 | 每个通道最多 1 条当前状态 | 状态流转历史永久或按审计周期保留 | 系统或技术 |
| 熔断策略 | 平台全局或通道组/通道维度 | `scope_type + scope_ref` 唯一 | 每个作用域最多 1 条 `ACTIVE` | 变更历史永久或按审计周期保留 | 技术或运营 |
| 错误码映射 | 上游通道 + 原始错误码 | `provider_code + raw_code` 唯一 | 每个原始错误码最多 1 条 `ACTIVE` | 变更历史永久或按审计周期保留 | 技术 |
| 重试策略 | 错误类别维度 | `normalized_category` 唯一 | 每个错误类别最多 1 条 `ACTIVE` | 变更历史永久或按审计周期保留 | 运营或技术 |
| 路由决策快照 | 每次发送或模拟 | 决策 ID 唯一 | 不限制，由消息量产生 | 与详单同生命周期 | 系统自动 |

若不同机构需要独立规则，版本作用域必须显式包含 `tenant_id` 或“全局”。不能通过命名习惯隐式区分。

### 5.2 路由策略版本

路由策略版本是一组规则的发布单元，不是一行备注字段。版本存在的意义是：

- 将多条规则作为一个整体校验、发布和回滚。
- 让每条消息记录当时使用的策略版本，便于问题复盘。
- 允许运营在新策略生效前做模拟验证。
- 避免直接编辑线上规则导致半更新状态。

V2 版本生命周期：

```text
DRAFT 草稿
→ VALIDATING 校验中
→ SCHEDULED 待生效
→ ACTIVE 生效中
→ SUPERSEDED 被新版本替代，或 ROLLED_BACK 因回滚操作退出生效
→ ARCHIVED 已归档
```

当前最小实现可只支持 `ACTIVE` 与 `SUPERSEDED`，但页面必须说明这是简化生命周期；正式生产应补齐草稿、校验、定时生效、回滚和归档。

#### 5.2.1 路由策略版本出现、变更与失效

| 阶段 | 何时出现 | 谁操作 | 数据动作 | 是否参与真实发送 | 如何失效 | 审计要求 |
|---|---|---|---|---|---|---|
| `DRAFT` | 运营新建版本或上传 CSV 但未发布 | 运营、技术 | 写入版本草稿和规则草稿 | 不参与 | 用户删除草稿或发布失败关闭 | 记录创建人、来源、规则数量 |
| `VALIDATING` | 用户点击校验、导入完成后系统校验目标引用和冲突 | 系统 | 校验通道、通道池、条件枚举、优先级冲突 | 不参与 | 校验通过或失败 | 记录校验结果、失败行号 |
| `SCHEDULED` | 用户选择未来生效时间 | 运营、技术 | 记录计划生效时间 | 到达生效时间前不参与 | 被取消、被新计划替换或到期生效 | 记录计划人和计划时间 |
| `ACTIVE` | 用户立即发布，或定时任务到达生效时间 | 运营、技术或系统定时任务 | 当前作用域旧 `ACTIVE` 进入 `SUPERSEDED`，新版本生效 | 参与新发送请求 | 新版本发布、回滚、人工停用 | 记录发布人、发布时间、替代版本 |
| `SUPERSEDED` | 新版本发布后自动产生 | 系统 | 旧版本变为只读 | 不参与新请求，但历史消息仍引用 | 可归档，不可删除已引用版本 | 记录被哪个版本替代 |
| `ROLLED_BACK` | 用户执行回滚，当前 `ACTIVE` 被新生成的回滚版本替代 | 运营、技术 | 当前版本退出生效并标记为已回滚；系统复制目标历史版本内容生成新的 `ACTIVE` 版本 | 不参与新请求，但历史消息仍引用 | 可归档，不可删除已引用版本 | 记录回滚原因、审批人、原当前版本、目标历史版本、新回滚版本 |
| `ARCHIVED` | 超过保留窗口或人工归档 | 运营、系统 | 只读保留 | 不参与 | 不允许物理删除有历史引用的版本 | 记录归档人和归档依据 |

规则：任何被历史发送、模拟或审计引用过的版本不得物理删除；只能失效或归档。

回滚不得直接把历史版本重新改为 `ACTIVE`。回滚必须生成一个新的版本号，新版本内容等于被选中的历史版本内容；回滚前的当前 `ACTIVE` 进入 `ROLLED_BACK`，同一作用域始终只能存在一个 `ACTIVE`。

完整生命周期阶段中，回滚生成的新版本必须先复用 `VALIDATING` 校验逻辑；若选择立即回滚，则校验通过后直接进入 `ACTIVE`，若选择计划回滚，则校验通过后进入 `SCHEDULED`。

### 5.3 路由规则

一条路由规则表示“当消息满足某个条件时，候选目标是什么”。规则不是自然语言说明，也不只是 CSV 文本，而是结构化策略行。

CSV 导入只是批量创建规则的输入格式。每行 CSV 对应一条规则。

V2 CSV 字段定义：

| 字段 | 示例 | 含义 | 约束 |
|---|---|---|---|
| `priority` | `10` | 优先级，数字越小越先匹配 | 同一版本内必须唯一 |
| `condition_type` | `CARRIER` | 匹配条件类型 | `CARRIER`、`PREFIX`、`TENANT`、`CONTENT_KEYWORD`、`TIME` |
| `condition_value` | `MOBILE` | 匹配条件值 | 根据条件类型解释 |
| `target_type` | `CHANNEL` | 目标类型 | `CHANNEL`、`POOL`、`DEFAULT`；权重选择是 `POOL` 的选择模式，不是独立目标类型 |
| `target_ref` | `CH_MAIN` | 目标引用 | 通道编码、通道池编码或默认目标 |
| `selection_mode` | `PRIMARY` | 通道池选择模式 | `PRIMARY`、`WEIGHTED`、`ROUND_ROBIN`；仅 `POOL` 目标需要 |

V2 页面必须明确展示：

- 当前生效版本包含多少条规则。
- 每条规则属于哪个版本。
- 规则按什么顺序匹配。
- 未命中规则时走什么默认目标。
- 规则目标如果被熔断，是否跳过并继续找下一条可用规则。
- 导入新版本会如何影响旧版本和旧规则。
- 同一版本内 `priority` 必须唯一；导入时发现重复优先级、重复条件或条件重叠导致同一消息可能命中多条同优先级规则时，必须阻止发布并展示冲突行号。

#### 5.3.1 路由规则出现、有效、失效与审计

| 问题 | V2 要求 |
|---|---|
| 规则什么时候出现 | 用户导入 CSV、在页面新增单条规则、复制历史版本生成新版本时出现。规则必须隶属于一个版本，不能脱离版本独立存在。 |
| 谁可以创建 | 运营可创建业务规则，技术可创建兜底和故障切换规则；财务、销售和客户默认只读。 |
| 怎么设定有效 | 规则本身有效必须同时满足：所属版本 `ACTIVE`、规则状态 `ACTIVE`、当前时间在有效期内、作用域匹配、目标引用存在。 |
| 怎么设定无效 | 规则可被人工禁用、因版本失效而失效、因有效期结束而失效、因目标通道/通道池停用而运行时不可用。 |
| 失效由谁触发 | 人工禁用由运营/技术触发；版本失效由发布新版本触发；目标失效由通道管理或通道健康触发；时间失效由系统自动判断。 |
| 历史引用怎么办 | 发送决策快照必须保存当时的版本号、规则 ID、规则摘要、目标和熔断状态，即使规则后来失效也能解释当时为什么这么路由。 |
| 规则最多多少条 | 每个有效版本默认最多 200 条；超过时必须支持分页、冲突检测、批量校验和发布前模拟覆盖率检查。 |
| 冲突怎么处理 | `VALIDATING` 阶段必须拒绝同一版本内重复 `priority` 或重复 `condition_type + condition_value` 的配置；由于 `priority` 必须唯一，系统不得依赖导入顺序或数据库 ID 决胜。 |

#### 5.3.2 规则与熔断的配置关系

熔断不应直接“配置在规则里”成为规则字段，而应作为规则目标的运行态过滤条件：

```text
规则命中条件
→ 得到目标 target_ref
→ 查询 target_ref 对应通道或通道池成员的熔断状态
→ CLOSED 可用
→ OPEN 跳过或切换备用目标
→ HALF_OPEN 只允许探测流量
```

规则中只配置“目标是谁”和“备用关系如何选择”；熔断状态由系统根据通道运行结果实时维护。若需要配置熔断阈值，应单独建“通道健康策略”或“熔断策略”，不要把失败次数阈值写进每条路由规则。

V2 规则目标类型要求：

| 目标类型 | 含义 | 熔断处理 |
|---|---|---|
| `CHANNEL` | 指向单个通道 | 目标 `OPEN` 时跳过该规则或返回无可用通道 |
| `POOL` | 指向通道池 | 过滤 `OPEN` 成员，从剩余成员中按 `selection_mode` 做主备、权重或轮询选择 |
| `DEFAULT` | 指向默认兜底目标 | 默认目标也必须接受熔断过滤 |

页面必须把“规则配置”和“熔断过滤”分开展示：规则说明为什么选中候选目标，熔断说明为什么该候选目标当前可用或不可用。

V2 不引入独立“权重组”对象。权重是通道池成员属性，通道池由通道管理模块维护，规则只引用通道池编码和选择模式。若未来需要独立权重组，必须另行提交 PRD 变更和数据模型评审。

当规则目标或通道池中的全部成员都因熔断、停用、配额不足或权限限制而不可用时，系统必须按以下顺序处理：

1. 在当前机构版本内继续寻找下一条可命中的候选规则。
2. 当前机构版本无可用目标时，按显式配置回落到全局 `ACTIVE` 版本。
3. 全局版本仍无可用目标时，尝试默认兜底目标。
4. 所有目标均不可用时，拒绝本次发送并返回 `NO_AVAILABLE_CHANNEL`，同时写入决策快照，说明每个候选目标被排除的原因。

### 5.4 路由模拟

路由模拟不是发送短信，也不扣费，不创建正式发送任务。它是运营和技术在发布前或排障时使用的“决策预演”。

模拟输入：

| 输入 | 来源 | 用途 |
|---|---|---|
| 机构 | 客户档案或排障对象 | 验证机构专属规则 |
| 运营商 | 号码归属识别或手工输入 | 验证运营商条件 |
| 号段 | 手机号前缀或号码归属库 | 验证号段条件 |
| 内容 | 模板渲染后的最终文本摘要 | 验证关键词条件 |
| 错误类别 | 回执归一化类别 | 预览失败后重试策略 |

模拟输出：

- 命中的策略版本。
- 命中的规则 ID。
- 目标类型和目标引用。
- 目标当前熔断状态。
- 命中的重试策略。
- 决策解释文本。
- 模拟记录快照，供排障审计。

模拟生命周期：

```text
录入样本
→ 读取当前候选策略与运行状态
→ 执行匹配
→ 写入模拟/决策历史
→ 展示解释
→ 用于人工判断是否发布、回滚或调整
```

### 5.5 熔断状态

熔断状态表示某个通道当前是否可进入路由候选。它不是路由规则本身，而是路由执行时的动态过滤条件。

V2 熔断状态：

| 状态 | 含义 | 对路由影响 |
|---|---|---|
| `CLOSED` | 通道正常 | 可作为候选目标 |
| `OPEN` | 通道异常，已熔断 | 不应作为候选目标，系统应选择备用目标 |
| `HALF_OPEN` | 恢复探测中 | 只允许小流量或探测请求 |

熔断数据来源：

- 上游发送失败。
- 上游超时。
- 通道健康检查失败。
- 投诉或人工暂停联动。
- 技术运维手工记录一次失败或成功。

熔断生命周期：

```text
通道正常 CLOSED
→ 连续失败或延迟超阈值
→ 打开熔断 OPEN
→ 路由跳过该通道
→ 到达探测条件
→ 半开 HALF_OPEN
→ 探测成功后 CLOSED
→ 探测失败后继续 OPEN
```

页面必须明确：手工“记录失败”是运维干预动作，会改变通道状态；它不是普通备注。

#### 5.5.1 熔断状态出现、有效、失效与恢复

| 问题 | V2 要求 |
|---|---|
| 熔断数据什么时候出现 | 第一次发送结果、通道健康检查、人工记录成功/失败、投诉联动或通道暂停事件发生时，为对应通道创建或更新状态。 |
| 谁可以操作 | 系统自动更新；技术运维可人工记录成功/失败或恢复；运营可在投诉、通道质量场景发起暂停或恢复申请。 |
| 当前状态有几条 | 每个通道最多一条当前熔断状态；状态历史可有多条事件记录。 |
| 什么时候有效 | 状态记录为 `OPEN` 且未到恢复探测条件时，对路由立即有效，目标不得进入普通候选。 |
| 什么时候失效 | 成功探测关闭熔断、人工恢复、通道被永久下线、或新健康策略重置状态时失效。 |
| 谁让它失效 | 自动探测成功由系统触发；人工恢复由技术或运营触发；通道下线由通道管理流程触发。 |
| 历史怎么审计 | 路由决策快照保存当时的通道熔断状态；即使后来恢复，也能解释历史消息为什么跳过该通道。 |

#### 5.5.2 熔断事件生命周期

```text
通道首次进入候选
→ 系统发现没有熔断记录
→ 创建默认 CLOSED 状态
→ 发送或健康检查产生失败
→ 失败事件写入熔断事件历史
→ 连续失败达到阈值
→ 当前状态变为 OPEN
→ 后续路由跳过该通道
→ 到达探测时间或人工发起恢复
→ 状态变为 HALF_OPEN
→ 探测成功变 CLOSED，探测失败回 OPEN
```

熔断事件必须记录来源类型：

| 来源类型 | 说明 | 可信级别 |
|---|---|---|
| `SEND_FAILURE` | 真实发送失败或超时 | 高 |
| `HEALTH_CHECK` | 通道健康检查失败 | 高 |
| `COMPLAINT_LINKED` | 投诉或监管风险触发 | 中高 |
| `MANUAL_OPERATION` | 人工记录失败或恢复 | 取决于审批与备注 |
| `MOCK_SIMULATION` | 测试流量或模拟环境产生 | 仅测试，不得污染生产 |

#### 5.5.3 熔断策略对象

熔断阈值必须独立为“熔断策略”，不得散落在路由规则、通道备注或页面文案中。

| 字段 | 要求 |
|---|---|
| 作用域 | 支持平台全局、通道组、单通道；优先级为单通道高于通道组高于全局 |
| 失败阈值 | 在滚动窗口内达到多少失败或超时后打开熔断 |
| 延迟阈值 | 平均或分位延迟超过阈值时可触发熔断或告警 |
| 滚动窗口 | 明确统计窗口，例如最近 N 次或最近 N 秒 |
| 半开探测量 | `HALF_OPEN` 状态允许的探测请求数量或比例 |
| 冷却时间 | `OPEN` 后进入 `HALF_OPEN` 前的最短等待时间 |
| 状态 | `DRAFT`、`ACTIVE`、`DISABLED`、`SUPERSEDED` |
| 所有人 | 负责人、审批人、最近操作人 |

熔断策略生效后，只影响后续事件如何改变通道熔断状态；已经写入的历史熔断事件和发送决策快照不得被重算。

### 5.6 重试策略

重试策略决定消息在收到失败、未知、待确认等结果后是否再次进入发送队列。

重试策略发生在上游回执或内部失败归一化之后，不发生在用户提交前，也不替代路由规则。

V2 错误类别：

| 类别 | 含义 | 默认动作 |
|---|---|---|
| `SUCCESS` | 已成功或最终成功 | 不重试 |
| `FAILURE` | 明确失败且允许重试 | 延迟后重试 |
| `PENDING` | 上游未给最终结果 | 等待或有限重试查询 |
| `UNKNOWN_REVIEW_REQUIRED` | 未知结果，需要人工复核 | 不自动无限重试，进入复核或有限重试 |

重试生命周期：

```text
发送任务提交上游
→ 收到回执或内部异常
→ 错误码归一化为类别
→ 查询当前重试策略
→ 判断 retryable
→ 生成下一次重试任务或终止
→ 达到最大次数后形成最终失败
→ 触发详单、回调、计费冲正或人工复核
```

页面必须明确：

- 保存重试策略会影响后续失败任务，不应无声改变历史任务。
- `maxAttempts` 是最大尝试次数，不是无限重试。
- `delaySeconds` 是下一次重试等待时间。
- 成功类结果不应触发重试。

#### 5.6.1 重试策略出现、有效、失效与历史任务

| 问题 | V2 要求 |
|---|---|
| 重试策略什么时候出现 | 系统初始化默认策略、运营新增错误类别策略、技术新增上游错误码归一化类别时出现。 |
| 谁可以操作 | 技术定义错误类别和安全边界；运营可在边界内调整是否重试、延迟和次数；客户不可操作平台级重试策略。 |
| 一共可以多少条 | 每个归一化错误类别最多一条 `ACTIVE` 策略；类别数量由错误码 taxonomy 控制，默认不少于 `SUCCESS`、`FAILURE`、`PENDING`、`UNKNOWN_REVIEW_REQUIRED`。 |
| 什么时候有效 | 策略状态为 `ACTIVE`，且失败任务进入该归一化类别时有效。 |
| 什么时候失效 | 被新策略版本替代、人工禁用、错误类别废弃或系统安全策略强制停用时失效。 |
| 谁让它失效 | 技术或运营人工停用；系统在错误类别废弃或安全阈值触发时停用。 |
| 历史任务怎么办 | 任务生成重试计划时必须保存当时策略快照；策略后来失效不改变已生成的历史决策，但未执行的重试任务是否重算必须有明确策略。 |

#### 5.6.2 重试策略与任务生命周期

```text
发送任务 PENDING
→ 上游返回失败/未知/超时
→ 错误码归一化
→ 查询当前 ACTIVE 重试策略
→ 写入本次失败处理快照
→ retryable=false：任务进入最终失败或人工复核
→ retryable=true 且次数未耗尽：生成下一次计划执行时间
→ 重试执行
→ 成功则最终成功
→ 次数耗尽仍失败则最终失败
```

未执行的重试任务必须有策略快照字段：

| 字段 | 目的 |
|---|---|
| 策略类别 | 说明为什么会重试或不重试 |
| 策略版本或更新时间 | 证明使用了哪一版策略 |
| 最大次数 | 防止无限重试 |
| 已尝试次数 | 解释当前进度 |
| 下一次执行时间 | 让运营和客户知道等待多久 |
| 终止原因 | 说明为什么不再重试 |

#### 5.6.3 错误码归一化与未执行重试任务

上游原始错误码不能直接驱动业务重试，必须先映射为归一化错误类别。

错误码映射对象必须包含：

| 字段 | 要求 |
|---|---|
| 上游通道 | `provider_code` 或通道编码 |
| 原始错误码 | 上游返回的原始 code 和 message 摘要 |
| 归一化类别 | 映射到 `SUCCESS`、`FAILURE`、`PENDING`、`UNKNOWN_REVIEW_REQUIRED` 或扩展类别 |
| 是否可重试建议 | 给重试策略的默认建议，不直接替代策略 |
| 生效状态 | `ACTIVE`、`DISABLED`、`SUPERSEDED` |
| 变更原因 | 新通道接入、上游码表变更、投诉或质量复盘 |
| 操作审计 | 创建人、审批人、生效时间、失效时间 |

同一上游通道同一原始错误码同时只能有一条 `ACTIVE` 映射。未知原始错误码默认归入 `UNKNOWN_REVIEW_REQUIRED`，不得自动无限重试。

未执行的重试任务采用“生成时快照优先”：

- 已生成的重试任务继续使用生成时保存的重试策略快照，不因后续策略变化自动重算。
- 新产生的失败任务读取当时 `ACTIVE` 的错误码映射和重试策略。
- 紧急风险场景需要改变已生成重试任务时，必须执行“取消/重排重试批次”动作，记录操作人、原因、影响任务数、原策略快照和新策略快照。
- 被取消或重排的任务在客户详单和审计中必须能看到原计划与变更原因。

## 5.7 规则、熔断、重试的跨对象生命周期

一条真实短信发送时，规则、熔断、重试并不是同时发生，而是按阶段依次参与：

| 阶段 | 参与对象 | 读取/写入 | 用户可见解释 |
|---|---|---|---|
| 策略准备 | 版本、规则 | 写入版本和规则 | “这批规则将决定后续新消息如何选择通道” |
| 提交短信 | 规则 | 读取当前 `ACTIVE` 版本规则 | “这条消息按哪个条件命中了哪条规则” |
| 通道选择 | 熔断状态 | 读取通道当前状态 | “命中目标是否可用，是否被跳过” |
| 发送失败 | 熔断状态 | 写入失败事件，可能改变状态 | “失败是否导致通道熔断” |
| 回执处理 | 重试策略 | 读取错误类别策略 | “失败后是否再试、多久后再试” |
| 任务终态 | 决策快照 | 写入最终状态和策略快照 | “历史上为什么这么处理，即使规则已失效也可解释” |

## 5.8 失效语义

失效必须区分“配置失效”和“运行时不可用”：

| 类型 | 示例 | 对历史影响 | 对新请求影响 |
|---|---|---|---|
| 版本失效 | 新版本发布导致旧版本 `SUPERSEDED` | 历史仍引用旧版本 | 新请求不再读取旧版本 |
| 规则失效 | 规则被禁用或所属版本失效 | 历史快照仍显示当时规则 | 新请求不再命中 |
| 目标失效 | 通道停用或删除前迁移 | 历史显示当时目标 | 新请求必须阻止发布或跳过 |
| 熔断失效 | 通道恢复为 `CLOSED` | 历史仍显示当时 `OPEN` | 新请求可重新进入候选 |
| 重试策略失效 | 类别策略被新策略替代 | 历史重试计划保留旧快照 | 新失败任务使用新策略 |

任何“失效”都必须记录：失效类型、触发人或触发系统、触发时间、原因、影响范围、可回滚性。

## 5.9 历史规则审计

如果历史发送使用的是后来失效的规则，审计页面必须能回答：

- 当时使用的策略版本是什么。
- 当时命中的规则 ID 和规则摘要是什么。
- 当时目标通道或通道池是什么。
- 当时目标的熔断状态是什么。
- 当时失败后使用了哪条重试策略。
- 该规则后来为什么失效，由谁操作，什么时候失效。
- 失效是否影响该历史消息的计费、回调或最终状态。

审计记录必须保存快照，而不能只保存外键。因为外键指向的规则、通道、策略后续可能被修改、失效或归档。

## 5.10 跨实践、跨用户、跨信息验证

V2 评审不得只由前端或单一角色确认，必须从三个维度验证。

### 5.10.1 跨实践验证

| 实践 | 验证问题 |
|---|---|
| 产品 | 用户是否能不用读代码就理解对象关系和生命周期 |
| 运营 | 是否能解释发布规则后哪些消息会受影响 |
| 技术 | 是否能追踪一条消息的决策快照和状态变化 |
| 财务 | 是否能判断通道切换是否影响成本、账单和冲正 |
| 客服 | 是否能向客户解释失败、延期、重试和最终状态 |
| 测试 | 是否能通过自动化用例验证每个生命周期状态和历史审计 |

### 5.10.2 跨用户验证

| 用户 | 必须能回答 |
|---|---|
| 运营用户 | 我导入了几条规则、何时生效、旧版本去哪了 |
| 技术用户 | 为什么这条消息选了这个通道、为什么跳过某通道 |
| 财务用户 | 这次通道切换是否影响价格快照和结算口径 |
| 客服用户 | 客户问失败原因时，我能否看到可解释链路 |
| 客户用户 | 我看到的是最终失败、等待重试，还是人工复核 |

### 5.10.3 跨信息验证

| 信息类型 | 验证问题 |
|---|---|
| 配置数据 | 版本、规则、熔断、重试是否有清晰当前态 |
| 事件数据 | 发布、失效、熔断、重试是否有事件流 |
| 业务数据 | 消息、账单、回调是否能引用当时决策快照 |
| 审计数据 | 谁在何时因为什么改变了策略或状态 |
| 展示数据 | 页面是否把“当前态”和“历史态”明确区分 |

## 6. 完整业务流

### 6.1 生产发送流

```text
客户提交短信
→ API/CMPP 鉴权
→ 幂等检查
→ 签名和模板可用性校验
→ 模板变量渲染为最终内容
→ 黑名单、内容安全、频控检查
→ 号码归属识别得到运营商和号段
→ 路由规则按优先级匹配候选目标
→ 熔断状态过滤不可用通道
→ 选出通道或通道池成员
→ 创建发送任务
→ 上游通道返回受理或失败
→ 回执错误码归一化
→ 查询重试策略
→ 重试、终止或进入人工复核
→ 更新详单、计费、回调、统计、告警
```

### 6.2 策略发布流

```text
运营准备规则 CSV
→ 上传或粘贴规则
→ 系统解析每行规则
→ 校验字段、目标引用和冲突
→ 生成策略版本
→ 模拟典型样本
→ 审核或确认发布
→ 版本生效
→ 新发送请求读取新版本
→ 历史发送继续保留旧版本快照
```

### 6.3 排障流

```text
客户反馈失败
→ 客服或技术定位消息 ID
→ 查看消息路由决策快照
→ 查看当时策略版本、命中规则、通道状态、重试策略
→ 如需复现，使用相同机构、运营商、号段、内容、错误类别做模拟
→ 判断是规则配置、通道熔断、回执归一化、重试策略还是客户数据问题
→ 采取调整策略、恢复通道、修改重试策略或解释客户原因
```

## 7. 数据流

### 7.1 输入数据

| 输入 | 生成者 | 写入时机 | 使用者 |
|---|---|---|---|
| 路由规则 CSV | 运营 | 策略导入时 | 路由策略服务 |
| 通道状态 | 技术系统、运维、通道健康检查 | 发送失败、健康检查、人工干预 | 路由决策 |
| 号码归属 | 号码归属服务 | 提交时或归属库更新时 | 路由规则匹配 |
| 消息内容 | 客户提交，模板渲染 | 发送提交时 | 内容条件和审计 |
| 回执错误码 | 上游通道 | 回执到达时 | 归一化和重试策略 |
| 重试策略 | 运营或技术 | 策略维护时 | 失败任务调度 |

### 7.2 输出数据

| 输出 | 写入原因 | 下游使用者 |
|---|---|---|
| 策略版本 | 发布或导入规则 | 路由决策、审计、回滚 |
| 活跃规则集 | 当前生效版本 | 发送路由、模拟路由 |
| 路由决策快照 | 每次模拟或正式发送 | 排障、详单、审计 |
| 熔断状态 | 通道失败、成功或人工干预 | 路由候选过滤、告警 |
| 重试任务 | 失败且可重试 | 调度器、详单、回调 |
| 最终发送状态 | 成功、失败、超限、复核 | 客户查询、计费、统计 |

### 7.3 数据保留与审计

- 策略版本和规则不能物理覆盖，应保留历史状态和操作人。
- 每条正式发送任务必须保存路由决策快照，包括策略版本、命中规则、目标、熔断状态和重试策略摘要。
- 熔断状态的每次改变必须记录来源：自动检测、上游失败、人工记录、投诉联动。
- 重试策略变更必须记录操作人、变更前值、变更后值和影响范围。
- 模拟记录可按运营审计周期保留，不得与正式发送详单混淆。

## 8. 指令流与动作契约

### 8.1 导入策略版本

| 项目 | 要求 |
|---|---|
| 触发用户 | 运营、技术运维、具备导入权限的平台管理员 |
| 目标对象 | 一个策略版本和其中 N 条规则 |
| 前置条件 | 版本号唯一；CSV 可解析；目标通道或通道池存在；操作者有权限 |
| 输入 | 版本号、来源、计划生效时间、规则 CSV |
| 执行结果 | 创建新版本；规则按优先级保存；根据发布模式进入草稿、待生效或生效 |
| 失败反馈 | 显示错误行号、字段名、错误原因和修复示例 |
| 审计 | 操作人、版本号、规则数量、来源、发布时间、结果 |
| 用户必须看到 | 当前版本规则总数、是否已生效、旧版本状态、影响范围 |

### 8.2 模拟路由

| 项目 | 要求 |
|---|---|
| 触发用户 | 运营、技术运维、客服二线 |
| 目标对象 | 一组输入样本和当前策略状态 |
| 前置条件 | 至少存在一个可用于模拟的策略版本 |
| 输入 | 机构、运营商、号段、内容、错误类别 |
| 执行结果 | 返回命中规则、目标、熔断状态、重试策略、解释文本 |
| 失败反馈 | 明确是无规则、目标不存在、通道熔断、输入不合法还是系统错误 |
| 审计 | 输入摘要、命中结果、操作者、时间 |
| 用户必须看到 | 模拟不会真实发送、不会扣费、不会改变任务状态 |

### 8.3 记录熔断事件

| 项目 | 要求 |
|---|---|
| 触发用户 | 技术运维、运营 |
| 目标对象 | 单个通道的运行状态 |
| 前置条件 | 通道存在；操作者有写权限；必须填写原因或来源 |
| 输入 | 通道编码、成功或失败、延迟、原因 |
| 执行结果 | 更新失败次数、成功次数、熔断状态、历史轨迹 |
| 失败反馈 | 通道不存在、权限不足、状态冲突、系统错误 |
| 审计 | 操作人、通道、前状态、后状态、原因、traceId |
| 用户必须看到 | 该动作会影响后续路由候选，不只是记录备注 |

### 8.4 保存重试策略

| 项目 | 要求 |
|---|---|
| 触发用户 | 运营、技术运维 |
| 目标对象 | 某个归一化错误类别 |
| 前置条件 | 错误类别合法；参数在安全边界内；操作者有写权限 |
| 输入 | 错误类别、是否可重试、延迟秒数、最大尝试次数 |
| 执行结果 | 后续失败任务按新策略执行 |
| 失败反馈 | 参数越界、类别非法、权限不足、保存失败 |
| 审计 | 变更前后值、操作者、影响范围 |
| 用户必须看到 | 该策略影响未来任务，不改写已完成历史 |

## 9. 页面信息架构要求

页面必须按用户理解路径组织，而不是按接口顺序堆叠控件。

### 9.1 顶部总览

顶部必须回答四个问题：

- 这个页面控制哪段业务链路。
- 当前是否影响真实发送。
- 当前生效版本、规则数量、熔断通道数量、可重试类别数量。
- 最近一次策略变更是谁在什么时候做的。

### 9.2 生产链路图

页面必须展示从客户提交到最终状态的链路图，并高亮本页面控制的节点：

```text
提交 → 合规 → 风控 → 路由规则 → 熔断过滤 → 通道发送 → 回执归一化 → 重试策略 → 最终状态
```

每个节点必须能说明输入、输出和下游影响。

### 9.3 对象关系卡

页面必须展示“版本、规则、模拟、熔断、重试”的关系：

- 版本包含规则。
- 模拟读取版本、熔断和重试策略。
- 熔断过滤目标。
- 重试处理失败结果。
- 决策快照连接消息详单和排障。

### 9.4 分区顺序

推荐页面顺序：

1. 业务链路与影响范围。
2. 当前生效状态总览。
3. 策略版本与规则管理。
4. 模拟路由与决策解释。
5. 熔断状态与通道影响。
6. 重试策略与失败动作。
7. 历史版本、模拟记录和审计。

## 10. 字段与表格展示要求

### 10.1 版本表

必须展示：

- 版本号。
- 状态。
- 规则数量。
- 来源。
- 生效时间。
- 创建人。
- 创建时间。
- 是否当前生产使用。
- 可执行动作：查看规则、模拟、发布、回滚、归档。

### 10.2 规则表

必须展示：

- 优先级。
- 条件类型。
- 条件值。
- 目标类型。
- 目标引用。
- 选择模式；若目标为 `POOL` 且选择模式为 `WEIGHTED`，只读展示通道池成员权重摘要，不在规则表存储独立权重。
- 所属版本。
- 状态。
- 人类可读解释，例如“移动号段命中后走 CH_MAIN”。

### 10.3 模拟结果

必须拆解展示：

- 输入样本。
- 候选规则数量。
- 命中规则。
- 跳过规则及原因。
- 目标通道当前熔断状态。
- 最终目标。
- 命中的重试策略。
- 是否会在真实发送中产生相同结果。

### 10.4 熔断表

必须展示：

- 通道编码。
- 当前状态。
- 连续失败次数。
- 成功次数。
- 最近延迟。
- 打开熔断时间。
- 最近来源。
- 对路由影响。
- 恢复条件。

### 10.5 重试表

必须展示：

- 错误类别。
- 是否可重试。
- 延迟秒数。
- 最大尝试次数。
- 状态。
- 最近更新人。
- 最近更新时间。
- 影响的消息状态流。

## 11. 状态与生命周期规则

### 11.1 版本状态规则

- 同一作用域同一时刻只允许一个生产 `ACTIVE` 版本。
- 新版本发布后，旧版本进入 `SUPERSEDED`。
- 已完成发送的消息继续保留当时使用的版本快照，不因新版本发布而改变。
- 回滚必须复制目标历史版本生成新的 `ACTIVE` 版本，并生成审计记录；不得静默恢复旧版本。

### 11.2 规则匹配规则

- 规则按优先级升序匹配。
- 匹配条件成立后，仍需检查目标状态。
- 如果目标熔断，应跳过或按策略进入备用目标。
- 无规则命中时走默认目标；默认目标必须可见、可配置、可审计。

### 11.3 熔断状态规则

- 连续失败达到阈值后进入 `OPEN`。
- `OPEN` 状态下不得作为普通发送候选。
- 恢复必须经过成功探测或人工恢复动作。
- 手工变更必须填写原因并记录审计。

### 11.4 重试状态规则

- `SUCCESS` 不重试。
- 可重试失败必须受最大次数限制。
- 不可归类错误不得无限重试。
- 重试耗尽后形成最终失败，并进入详单、回调和必要告警。

## 12. 权限与审计

| 能力 | 读取权限 | 写入权限 | 导入权限 | 审计要求 |
|---|---|---|---|---|
| 查看版本与规则 | 必须 | 不需要 | 不需要 | 记录敏感导出 |
| 导入策略 | 必须 | 建议 | 必须 | 记录版本、规则数、来源 |
| 模拟路由 | 必须 | 需要执行权限，不改变生产数据 | 不需要 | 记录输入摘要和结果 |
| 记录熔断 | 必须 | 必须 | 不需要 | 记录前后状态和原因 |
| 保存重试策略 | 必须 | 必须 | 不需要 | 记录变更前后值 |

角色权限必须由现有 RBAC 或可配置角色能力表达，不得依赖页面隐藏按钮代替后端授权：

| 角色 | 默认能力 |
|---|---|
| 平台管理员 | 全量读取、导入、发布、回滚、熔断干预、重试策略维护、模拟器启停 |
| 运营 | 读取、导入草稿、发起发布、模拟路由、发起通道暂停/恢复申请 |
| 技术运维 | 读取、发布/回滚、熔断干预、错误码映射、重试安全边界、模拟器启停 |
| 财务 | 只读查看通道切换、价格快照、模拟流量是否计入账务 |
| 客户成功/客服二线 | 读取决策解释、历史快照，并可执行只读模拟路由；默认不得导入、发布、改熔断、改重试 |
| 客户管理员 | 只读查看本机构详单解释，不得查看其他机构策略细节 |

如果当前系统没有“客户成功/客服二线”内置角色，V2 必须将其定义为自定义平台角色，最小权限为 `routing-policy:read`、`route-simulation:execute`、`decision-audit:read`。`route-simulation:execute` 只能创建模拟记录和解释结果，不得触发真实发送、扣费、熔断状态变更或生产任务状态变更。

## 13. 验收标准

### 13.1 用户理解验收

验收人员在不阅读代码的情况下，必须能从页面回答：

- 当前有几个生效版本，当前版本有几条规则。
- CSV 每一列是什么意思，导入后会产生什么对象。
- 版本为什么存在，新旧版本如何切换。
- 模拟路由什么时候使用，是否会真实发送或扣费。
- 熔断状态由什么触发，打开后对路由有什么影响。
- 重试策略在消息失败后的哪个阶段生效。
- 每个按钮点击后会改变哪些数据。

### 13.2 行为验收

- 导入策略后，页面显示版本、规则数、状态、生效时间和旧版本状态变化。
- 模拟路由后，页面展示输入、命中、跳过、熔断、重试、最终目标的完整解释。
- 记录通道失败后，页面展示状态变化和对后续路由的影响。
- 保存重试策略后，页面展示该类别未来失败任务的执行方式。
- 页面必须显式标识当前能力是否已接入真实发送链路。

### 13.3 数据验收

- 每次策略变更有版本记录和操作人。
- 每条规则能追溯到版本。
- 每次模拟有决策历史。
- 每次熔断变更有状态历史。
- 每次重试策略变更有审计证据。

## 14. 实施边界与约束

V2 已明确关键产品决策，实施时不得重新引入以下歧义：

| 主题 | V2 边界 |
|---|---|
| 路由策略源 | 版本化路由策略是新消息真实发送的唯一策略源；旧 `route_rules` 只允许兼容读取、只读展示或一次性迁移 |
| 生命周期范围 | 最小可交付支持 `ACTIVE`、`SUPERSEDED` 和决策快照；完整治理再补 `DRAFT`、`VALIDATING`、`SCHEDULED`、`ROLLED_BACK`、`ARCHIVED` |
| 目标引用 | `target_ref` 必须有统一解析规范，明确通道编码、通道池编码和默认目标的引用类型 |
| 熔断来源 | 上游失败、健康检查、投诉联动、人工操作必须统一进入熔断事件流，并由熔断策略决定当前状态 |
| 重试状态机 | 原始错误码先归一化，再由重试策略决定是否生成重试任务、最终失败、回调或人工复核 |
| 客户解释 | 客户侧详单至少展示本机构可见的失败原因、重试进度、最终状态和平台解释，不暴露其他机构或通道敏感配置 |

完整能力可分阶段实现，但每个阶段都必须有可执行验证证据，并且不能把未实现能力描述为已完成。

## 15. V2 成功标准

V2 成功不是页面多几段说明，而是用户能形成完整心智模型：

```text
规则决定“去哪发”
版本决定“哪组规则正在生效”
模拟决定“上线前或排障时预演结果”
熔断决定“这个目标现在还能不能用”
重试决定“失败后还要不要再试”
决策快照决定“事后能不能解释清楚”
```

只有当业务流、数据流、指令流和生命周期都在页面上可见、可验证、可审计时，路由、熔断与重试策略才算产品化完成。

## 16. 首页驾驶舱 V2 需求

### 16.1 产品定位

平台首页不应只是若干统计数字的列表，而应是运营驾驶舱。用户登录后第一眼应看到平台是否正常、业务是否增长、通道是否健康、财务是否有风险、客户发送是否顺畅。

首页驾驶舱面向平台管理员、运营、技术、财务和销售共同使用。它不替代各专项页面，但要提供跨系统总览和下钻入口。

### 16.2 驾驶舱布局

首页建议采用以下大盘布局：

```text
顶部：全局健康状态 + 时间范围 + 刷新/自动刷新
第一行：发送量、成功率、失败率、活跃机构、收入/成本、告警数
第二行：实时发送趋势折线图 + 状态分布环图
第三行：通道健康雷达/柱状图 + 机构发送排行
第四行：财务风险卡 + 投诉/退订风险卡 + 熔断/重试风险卡
底部：最近异常事件流和可下钻操作
```

### 16.3 必须图表化的数据

| 数据域 | 图表形态 | 说明 | 下钻目标 |
|---|---|---|---|
| 实时发送量 | 折线图 | 按分钟或小时展示提交、成功、失败 | 发送详单 |
| 成功率/失败率 | 双轴趋势或状态分布图 | 展示质量变化，不只给单点数值 | 通道健康、错误分析 |
| 活跃机构 | 排行榜 + 趋势 | 展示机构贡献和异常突增 | 机构详情 |
| 通道健康 | 柱状图或热力图 | 展示各通道成功率、延迟、熔断状态 | 通道监控 |
| 路由命中 | 桑基图或分布图 | 展示规则、通道、机构之间的流量分配 | 路由策略 |
| 重试队列 | 堆叠柱图 | 展示待重试、已重试、耗尽失败 | 重试策略/任务列表 |
| 财务风险 | 指标卡 + 趋势 | 展示余额不足、授信超限、欠费冻结 | 财务总览 |
| 投诉风险 | 趋势 + 排名 | 展示机构/通道投诉占比 | 投诉看板 |
| 告警事件 | 时间线 | 展示熔断、失败率、余额、投诉等事件 | 告警中心 |

### 16.4 驾驶舱数据口径

首页每个指标必须显示口径说明：

- 数据来源：消息任务、回执、通道健康、账务流水、投诉工单、告警事件。
- 时间范围：实时、今日、本周、本月或自定义。
- 刷新方式：自动刷新、手动刷新、批处理刷新。
- 数据延迟：回执延迟、统计聚合延迟、人工投诉录入延迟。
- 异常说明：未知归因、缺失回执、模拟流量是否计入。

模拟流量默认必须显式标识，避免与真实客户数据混淆。

### 16.5 首页启动/停止模拟按钮

首页增加“启动模拟发送”和“停止模拟发送”按钮，用于测试环境演示真实发送链路。

| 项目 | 要求 |
|---|---|
| 显示位置 | 首页驾驶舱顶部操作区或测试环境工具区 |
| 可见环境 | 仅测试、演示、开发环境显示；生产环境默认隐藏 |
| 可见性来源 | 前端必须读取后端返回的运行能力 `simulationEnabled`，该值来自服务端 profile 或配置，不得只用前端构建变量判断 |
| 权限 | 仅平台管理员或技术运维可操作 |
| 启动结果 | 服务端启动独立模拟任务线程或调度器，开始随机调用短信提交接口 |
| 停止结果 | 服务端停止模拟任务，不再发起新的模拟提交；已提交任务按正常链路完成 |
| 页面反馈 | 展示当前状态：未启动、运行中、停止中、异常停止 |
| 审计 | 记录启动人、停止人、时间、参数、运行批次 ID |

## 17. 测试流量模拟器 V2 需求

### 17.1 产品目标

测试流量模拟器用于在测试环境中持续产生近似真实客户发送的数据，让首页驾驶舱、路由、熔断、重试、回执、计费、详单和告警都能看到动态变化。

模拟器不是生产功能，必须有环境隔离和数据标识。

### 17.2 初始化数据要求

系统在测试环境初始化 5 个机构，每个机构 4 个已审核模板。

| 数据 | 数量 | 状态 | 约束 |
|---|---|---|---|
| 机构 | 5 个 | 已认证、可发送 | 每个机构有独立编号、账号、余额或试用额度 |
| 签名 | 每机构至少 1 个 | 已审核通过 | 模板默认绑定可用签名 |
| 模板 | 每机构 4 个 | 已审核通过 | 覆盖验证码、通知、营销、告警四类 |
| API Key | 每机构至少 1 个 | 有效 | 模拟器调用真实短信提交接口时使用 |
| 通道 | 至少 1 个 mock 通道 | 正常 | 最后一跳运营商连接使用 mock 模式 |

模板内容必须定义变量，模拟器生成的内容必须符合模板变量要求，不能绕过模板校验。

示例模板类型：

| 类型 | 模板示例 | 必填变量 |
|---|---|---|
| 验证码 | `您的验证码为${code}，5分钟内有效。` | `code` |
| 通知 | `尊敬的${name}，您的订单${orderNo}已处理。` | `name`、`orderNo` |
| 营销 | `${name}，本周活动${campaign}，回复TD退订。` | `name`、`campaign` |
| 告警 | `系统${systemName}出现${level}告警，请及时处理。` | `systemName`、`level` |

### 17.3 模拟发送线程

模拟器启动后，服务端以独立线程、调度任务或受控 worker 运行。每 1 分钟内随机发起若干短信调用接口。

V2 要求：

- 随机选择 5 个机构之一。
- 随机选择该机构 4 个已审核模板之一。
- 根据模板变量生成合法参数。
- 随机生成手机号，但必须满足号码归属识别和黑名单规则的测试边界。
- 使用该机构 API Key 调用真实短信提交接口，而不是绕过接口直接写数据库。
- 最后一跳运营商连接使用 mock 通道，模拟成功、失败、超时、未知状态。
- 每次模拟提交写入批次 ID，方便从首页过滤“模拟流量”。
- 模拟流量可以进入路由、熔断、重试、计费和统计链路，但必须在数据口径中标识。
- 模拟流量必须先经过签名、模板、黑名单、频控、余额或试用额度等真实入口校验；被拦截的请求记为 `COMPLIANCE_REJECTED` 或对应业务拒绝类型，不进入 mock 运营商成功/失败比例，也不得计入通道熔断失败。

### 17.4 模拟频率与安全边界

| 项目 | 要求 |
|---|---|
| 默认频率 | 每分钟内随机发起 1 到 N 次提交，N 由测试环境配置控制 |
| 上限 | 必须有硬上限，防止压垮本机 Docker 或污染统计 |
| 幂等 | 每次提交使用唯一 `submitId`，重复重试不得重复扣费 |
| 号码 | 使用测试号段或脱敏号码，不得使用真实用户手机号 |
| 环境 | 仅 dev/test/demo profile 启用 |
| 停止 | 停止后不得再创建新提交；已有任务按正常回执流程结束 |
| 可观测性 | 首页显示运行状态、最近提交时间、成功/失败/重试计数 |
| 额度耗尽 | 测试机构余额或试用额度不足时，该机构本次请求按真实入口拒绝处理；模拟器可跳过该机构继续选择其他可用测试机构，全部测试机构不可用时自动停止并展示原因 |

### 17.5 Mock 运营商模式

Mock 模式必须模拟真实运营商最后一跳，但不能调用真实外部供应商。

Mock 输出类型：

| 输出 | 比例 | 下游影响 |
|---|---|---|
| 成功受理 + 成功回执 | 可配置 | 产生成功详单和计费确认 |
| 成功受理 + 失败回执 | 可配置 | 触发重试策略或最终失败 |
| 请求超时 | 可配置 | 触发通道失败统计和可能熔断 |
| 未知状态 | 可配置 | 进入待确认或人工复核路径 |
| 通道异常 | 可配置 | 触发熔断或告警 |

Mock 结果必须带有 `mock=true`、批次 ID、机构 ID、模板 ID、通道 ID，供驾驶舱和详单过滤。

### 17.6 模拟器生命周期

```text
初始化测试机构、模板、签名、API Key、mock 通道
→ 首页点击启动模拟
→ 服务端创建模拟批次
→ 独立线程开始按随机间隔提交短信
→ 每次提交走真实 API 接入链路
→ mock 通道产生受理和回执结果
→ 路由、熔断、重试、计费、统计更新
→ 首页图表实时刷新
→ 用户点击停止
→ 停止创建新提交
→ 等待已提交任务自然收敛
→ 批次状态变为已停止
```

### 17.7 模拟器数据隔离

模拟器产生的数据必须与真实数据可区分：

- 机构标记为测试机构。
- 消息标记为模拟批次。
- 通道标记为 mock。
- 统计指标提供“包含模拟流量”和“排除模拟流量”两种口径。
- 财务数据默认不进入正式对账；如进入演示账务，必须标记为模拟账务。
- 导出和审计保留模拟标识。
- 合规、黑名单、频控或余额校验拒绝的模拟请求必须单独统计为入口拒绝，不得被误归因为运营商失败或通道熔断。

### 17.8 与真实业务链路的关系

模拟器不是绕过业务链路的数据生成器。它必须扮演“真实客户使用 API 发短信”的角色：

```text
测试机构 API Key
→ 真实短信提交接口
→ 签名与模板校验
→ 黑名单、频控、余额或试用额度校验
→ 路由策略与熔断过滤
→ mock 运营商通道
→ 回执归一化
→ 重试策略
→ 详单、统计、审计、驾驶舱
```

模拟器不得直接写消息表、详单表、统计表或熔断状态表。任何为了演示而生成的数据都必须通过正式服务接口或明确的测试专用种子接口进入系统。

## 18. 新增验收要求

### 18.1 PRD 完整性验收

评审人员必须从以下角度逐项验证：

| 角度 | 验收问题 |
|---|---|
| 跨实践 | 产品、运营、技术、财务、客服、测试是否都能解释对象生命周期 |
| 跨用户 | 平台管理员、运营、技术、财务、客户是否知道自己能做什么、看到什么 |
| 跨信息 | 当前态、历史态、事件流、审计流、统计流是否能互相追溯 |
| 跨环境 | 生产真实流量和测试模拟流量是否隔离 |
| 跨时间 | 当前规则失效后，历史消息是否仍能解释当时决策 |

PRD 完整性验收产出物必须包括：角色验收清单、生命周期状态机核对表、至少一条真实发送决策快照样例、至少一条模拟决策快照样例、权限矩阵核对结果。

### 18.2 首页驾驶舱验收

- 首页必须以图表和驾驶舱卡片展示关键指标，而不是只展示静态表格。
- 首页必须能看到发送量、成功率、失败率、通道健康、机构排行、路由命中分布、重试队列、财务风险、投诉风险、告警事件。
- 首页必须能启动和停止模拟发送器。
- 首页启停按钮和 §17.6 模拟器生命周期必须控制同一个后端模拟批次，不得实现为两套开关。
- 模拟器运行时，首页图表能看到数据变化，并能识别模拟流量。
- 首页图表必须展示数据刷新口径和最近刷新时间；模拟流量提交后，应在配置的刷新口径内进入趋势、路由命中和重试队列图表。

### 18.3 模拟器验收

- 测试环境初始化 5 个机构。
- 每个机构有 4 个已审核模板。
- 模拟器只使用这些机构和模板生成合法请求。
- 模拟器通过真实短信提交 API 发起调用。
- 最后一跳运营商使用 mock 模式。
- 启动后每分钟内随机产生提交。
- 停止后不再产生新的提交。
- 模拟流量可在首页、详单、统计、审计中识别和过滤。
- 模拟器达到配置硬上限后停止新增提交，并在首页展示已达上限或受限状态。
- 重复提交同一 `submitId` 不得产生二次任务、二次扣费或重复统计。
- 黑名单、频控、余额不足、模板不匹配等入口拒绝必须单独统计，不计入 mock 运营商成功/失败比例，也不计入通道熔断失败计数。
- 模拟器 worker、线程或调度任务停止、异常退出时，不得阻塞真实 API 接入和已提交任务的后续处理。
- 全部测试机构因余额、额度、模板或权限不可用时，模拟器自动停止新增提交，并在首页展示停止原因和最后一次拒绝类型。

### 18.4 分阶段验收标准

每个开发 phase 必须独立验收、独立提交、独立 PR，并在合并前提供可执行验证证据。

| Phase | 验收焦点 | 必须达成 |
|---|---|---|
| Phase 0 架构与 PRD 对齐 | 决策无歧义 | 真实路由策略源、旧表迁移边界、错误码归一化、回滚语义、权限角色、模拟环境边界全部写入 PRD 和计划 |
| Phase 1 最小路由治理闭环 | 新消息真实接入 | 新提交读取版本化 `ACTIVE` 策略；导入 CSV 产生版本和规则；旧版本进入 `SUPERSEDED`；每次真实发送保存决策快照 |
| Phase 2 熔断与重试治理 | 运行态可解释 | 熔断策略、熔断事件、错误码映射、重试策略和未执行重试快照可被查看、变更、审计 |
| Phase 3 全生命周期治理 | 操作安全 | 草稿、校验、定时生效、回滚生成新版本、归档只读、历史引用不可物理删除全部可验证 |
| Phase 4 首页驾驶舱 | 总览可理解 | 首页以图表展示发送、成功率、通道健康、路由命中、重试、财务风险、投诉风险和告警，并可下钻 |
| Phase 5 测试流量模拟器 | 测试环境可演示 | 5 个机构、每机构 4 个审核模板、模拟器启停、真实 API 调用、mock 运营商、模拟标识和过滤全部可验证 |

任一 phase 未达到其验收焦点时，不得进入“完成、合并、部署测试环境”的状态。
