## 3. 后期调整为何集中出现

### 3.1 PRD 覆盖广，但不是“动作完整”

V1 PRD 对模块、字段、状态机覆盖较全，但很多地方停留在“支持某功能”。例如告警历史、通知设置、状态管理、审核历史等页面，缺少每个按钮的动作契约：

- 用户点击前应该知道什么？
- 操作对象是哪一条记录还是当前筛选结果？
- 点击后页面、数据、审计日志分别如何变化？
- 失败时在哪里提示，是否允许重试？

因此实现时容易产出“页面上有按钮/输入框”，但用户看不懂，也无法形成稳定自动化验收。

### 3.2 视觉标准没有在第一批页面前冻结

多条 issue 都围绕查询区、控件宽度、按钮高度、四列布局、标签位置、空状态表头。这说明设计系统和页面验收规范是在页面已经大量存在后才变成硬约束。

正确顺序应是：

```text
页面骨架与设计 token
→ QueryPanel/Form/Table/Modal 基础组件
→ 每类页面样板验收
→ 批量业务页面实现
```

实际过程更像：

```text
批量页面实现
→ 发现视觉与交互不一致
→ 建规范
→ 逐页修复
```

这造成了大量后期布局 issue。

### 3.3 验收更关注“有无”，不足以验证“可用”

早期验收偏向：

- 页面是否存在。
- 字段是否渲染。
- 接口是否返回。
- test-id 是否可定位。

后期问题说明还需要验证：

- 查询输入后是否真的发请求或更新结果。
- 行级动作是否绑定当前行对象。
- 批量动作是否锁定完整目标集合。
- 原因、备注、审批意见是否只在对应动作弹窗中出现。
- 空状态、错误状态、加载状态是否都可理解。

### 3.4 跨模块主流程没有压到最前面

`#95` 修复了端到端 SMS 流中的关键缺口，包括发送调度、验证码路由最低通道价格、未知归因、账务使用通道价格/试用额度、HMAC HTTP API 等。这类问题不是单个页面 bug，而是“提交 → 审核 → 路由 → 发送 → 回执 → 计费 → 统计”的主链路在前期没有作为最小闭环优先压实。

如果最早用一条真实消息贯穿：

```text
试用机构
→ 已审核签名模板
→ HTTP 提交
→ 最终文本审核
→ 路由通道
→ 扣试用额度或计费
→ 回执
→ 详单
→ 投诉/统计可归因
```

很多计费、归因、状态、接口签名问题会更早暴露。

### 3.5 文档状态与实现状态存在漂移

项目中有 PRD、PRD Review、规划文档、phase 证据、issue、PR、前端规范。证据很充分，但分散在不同位置，且 `.planning/STATE.md` 这类状态文件可能落后于 merged PR 历史。

这会带来两个风险：

- 新开发者不知道哪个文档是最新验收口径。
- 产品缺口可能已经在 issue 中表达，但没有回写到 PRD 或统一规范。

## 4. 前期偏差总结

| 偏差 | 影响 | 后果 |
|---|---|---|
| 以功能模块拆解为主，业务闭环拆解不足 | 跨模块依赖晚暴露 | 试用、计费、路由、投诉归因后补 |
| UI 组件规范不是前置门槛 | 页面局部实现各自发挥 | 控件尺寸、查询区、表格空状态反复修 |
| 按钮缺少动作契约 | 页面可渲染但不可理解 | 告警按钮、原因输入框、状态管理按钮出问题 |
| 自动化偏结构，不够偏行为 | “有控件”通过，“有作用”不一定通过 | 孤立输入框、无异步反馈 |
| 发布验证不是每个阶段固定入口 | 本地可跑不等于 Docker 可发布 | 全新数据库、构建 commit、迁移一致性后期暴露 |
| 数据口径没有页面化 | 指标看似存在但用户不知可信度 | 投诉占比、容量指标、未知归因需补说明 |

## 5. 以后开发需要规避的经验

### 5.1 PRD 必须写“对象 + 动作 + 结果”

每个功能点至少补充：

- 谁可以操作。
- 操作哪个对象。
- 什么状态下可以操作。
- 必填哪些输入。
- 成功后哪些状态、数据、页面发生变化。
- 失败后如何提示和重试。
- 审计日志记录什么。
- 自动化如何证明。

缺少这些内容时，不应进入实现。

### 5.2 先做一个真实端到端薄切片

短信平台的最小薄切片应覆盖：

```text
机构试用
→ 签名模板
→ HTTP 鉴权提交
→ 内容/黑名单/频控
→ 路由
→ 发送任务
→ 回执
→ 扣费或试用额度
→ 详单查询
→ 告警/投诉可归因
```

只有这个薄切片可执行，后续扩展页面和模块才不容易偏离主流程。

### 5.3 UI 规范要作为首个业务页面的准入条件

在批量页面实现前，应先冻结：

- 页面骨架。
- QueryPanel。
- Form Modal/Drawer。
- DataTable/Empty State。
- 操作确认弹窗。
- `data-testid` 命名规则。
- Chrome + Playwright 验收脚本。

没有统一组件的页面不应批量复制实现。

### 5.4 所有输入控件必须有行为归属

输入控件只能属于以下三类之一：

- 查询条件：必须有搜索/重置，或清晰的自动联动说明。
- 表单字段：必须有保存/提交/取消/校验。
- 只读展示：必须渲染成文本或标签，不使用可编辑控件。

不满足三类之一就是孤立控件，应在 PRD 或设计评审时拦截。

### 5.5 所有行级状态动作必须放回行上下文

暂停机构、启用账号、恢复通道、确认告警、重推回调等动作必须让用户看到：

- 当前行对象是谁。
- 当前状态是什么。
- 操作后状态是什么。
- 影响范围是什么。
- 是否需要原因。

这能避免 `#90`、`#91` 类问题。

### 5.6 数据指标必须有口径卡片

所有报表、看板、统计卡片需展示或可查看：

- 指标定义。
- 数据来源。
- 刷新频率。
- 缺失/未知/人工录入限制。
- 最近更新时间。

否则“投诉占比”“成功率”“成本利润”等指标容易被误解。

### 5.7 发布环境必须纳入 DoD

每个可发布改动至少记录：

- 构建 commit。
- 数据库迁移状态。
- 全新数据库启动结果。
- Docker Web/Core 版本一致性。
- 默认测试账号是否可登录。
- 关键健康检查和登录接口验证。

这类验证不应等到最终发布前才补。

## 6. 建议新增开发门禁

| 门禁 | 检查问题 | 通过标准 |
|---|---|---|
| PRD 动作契约门禁 | 是否只有功能名，没有动作语义 | 每个按钮有目标、前置、结果、失败、审计 |
| 数据口径门禁 | 指标是否能解释来源和可信度 | 每个指标有定义、来源、刷新、限制 |
| UI 基线门禁 | 页面是否沿用统一组件 | QueryPanel/Form/Table/Modal 规范通过 |
| 行为自动化门禁 | 控件是否真的改变数据或视图 | Playwright/API 可观察请求或状态变化 |
| 主链路门禁 | 模块是否接入端到端流 | 至少一条真实业务路径跑通 |
| 发布门禁 | Docker 环境是否代表可交付状态 | 全新库、迁移、健康检查、登录验证通过 |
| 文档回写门禁 | issue 修复是否沉淀规则 | 需求变化回写 PRD/规范/验收脚本 |

## 7. 可立即回写 PRD V2 的条目

- 告警管理：补充每个按钮的动作语义、状态变化和页面反馈，直接回应 `#92`。
- 查询区：把 `docs/frontend页面实现规范.md` 的 QueryPanel 规则并入 PRD 页面验收。
- 表单：把四列布局、固定宽度、label 同行、按钮右侧动作区作为 PRD 硬性要求。
- 状态管理：所有行级状态变化必须在行内提供动作入口和确认弹窗。
- 原因输入：原因只能出现在动作确认弹窗中，且必须绑定目标对象。
- 试用/计费：明确试用额度、通道价格、客户价格版本、计费流水快照。
- 投诉归因：明确未知归因队列、口径提示和补充归因流程。
- Docker 发布：把默认账号、URL、健康检查、构建 commit 和迁移状态写入发布验收。

## 8. 结论

这些 issue 和 bug 的主要根因不是单纯编码粗心，而是前期 PRD 与验收方式对“业务可理解性”和“动作可执行性”的约束不足。后续应把 PRD 从功能列表升级为业务流、数据流、指令流三张图，并要求每个页面、按钮、指标、导出、状态变更都有可验证证据。这样才能减少后期靠 bug 单修正产品语义和交互规范的成本。
